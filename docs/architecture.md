# Architecture

shyspace is a team workspace (chat, pages, AI agents) where every device keeps a full, encrypted-in-transit copy of the data, and no server can read anything.

## The big picture

```
 Desktop app (Tauri + React)        shy CLI (MCP server for agents)
            │                                   │
            └───────────── shy-core ────────────┘
                   │            │           │
              SQLite (local)  iroh gossip  S3 bucket
                              (live, P2P)  (mailbox for offline members)
```

- **`crates/shy-core`**: the whole engine. Every client (desktop app, CLI, agents) is a thin layer on top of it.
- **`crates/shy-cli`**: the `shy` command. It runs a member without a UI and serves the workspace to AI agents over MCP.
- **`crates/shy-media`**: huddle audio, the only crate that knows about microphones, speakers and iroh-live. It implements the core's `HuddleMedia` once per workspace (`lib.rs`): each workspace's media node runs on that workspace's own endpoint, so its call, sounds and ring use its network and device key, while the devices and the one call at a time are shared; a workspace can stop or mute only its own call. `access` (the media node's policy: only the call's listed peers, each reading only this call's path and publishing only at its own), `call` (one running call: the publication, the speaker, a listener per peer, device checks), `listen` (hearing one peer: subscribe, decode, play, link and speaking reports), `mic` (mute closes the device; microphone state and your own speaking), `system` (the real devices through moq-audio and cpal), `devices` (which device opens, the Bluetooth rule, the device list), `cues` and `wav` (the join, leave and ring sounds bundled from `sounds/`, rendered by its `render.py`), `playout` (playing a whole sound through a stream that holds only a moment), and calls between endpoints with test tones in `tests/`.
- **`crates/shy-ffi`**: the core for the phone apps. UniFFI generates Swift and Kotlin from it. Like the Tauri command layer it maps calls one to one and holds no logic: `app` (the workspaces on the device, opening and creating), `workspace` (one workspace's calls and its change listener), `keys` (the app's keystore offered to the core as `HostKeyStore`), `android` (the one JNI call that lets HTTPS check certificates through the phone's trust store), `runtime` (the one Tokio runtime every call runs on, off the app's threads), `error`. The read models it returns are `views.rs` types, made usable from Swift and Kotlin by shy-core's `ffi` feature, so there is no second copy to keep in step. Bucket settings cross as an opaque object, so the secret key can't land in a generated type's text form. Its `memory-bucket` feature (also shy-core's) adds a workspace set on one in-memory bucket, for tests and demos only.
- **`apps/android`**: the Android app (Kotlin, Jetpack Compose, Material 3). Its Gradle build compiles `crates/shy-ffi` for the phone and for the build machine, generates the Kotlin bindings from the latter, and packages only `libshy_ffi.so`; debug builds add the in-memory bucket. `ShyspaceApplication` holds the one `ShyApp` per process and, before making it, hands the core the app's context (`PlatformTls`) so `rustls-platform-verifier` can check HTTPS certificates through Android's trust store (that crate's Kotlin half is vendored in `app/libs`, and the build fails if its version isn't the one `Cargo.lock` pairs with the Rust half). Device keys live in `AndroidDeviceKeyStore`: one file per account, sealed with AES-GCM under a key that never leaves the Android Keystore (made with the first key, never on a read, and never again once sealed keys exist), written to a synced temp file and renamed into place under a lock that refuses an existing key, then the folder synced. Screens are in `features/<feature>`, with a ViewModel where they load from the core; `features/settings` keeps the phone's own settings in DataStore (`AppSettings`, read once at start so the first frame already follows them), `features/network` asks for Android 17's local network permission when a bucket address resolves to a private, link-local or `.local` address (`LocalNetworkAccess`: a line on why, then Android's prompt, then the way to Settings after a refusal), navigation in `ShyspaceNavigation.kt` (Navigation 3: Home and You are tabs in `MainTabBar`, You sitting on Home so Back returns there, and switching tabs doesn't animate), and colours and motion in `ui/theme/ShyTokens.kt`, generated from the desktop stylesheet by `tools/design-tokens/export.mjs`.
- **`crates/shy-demo`**: a development tool that fills a fresh workspace with demo people and content, through the same `Workspace` API.
- **`vendor/yrs`**: a patched copy of the Yjs library the core merges pages with (see `vendor/README.md`).
- **`apps/desktop`**: the desktop app. `src-tauri/src/lib.rs` maps each UI command to one `Workspace` call and forwards core changes to the UI as `change` events; `src-tauri/src/updates.rs` finds, downloads and installs app updates. `src-tauri/src/tray.rs` is the app's icon outside its window: the tray on Linux and Windows (the app icon, or a one-colour planet that matches the panel), on macOS an optional menu bar item (a template planet) beside the Dock, and the unread count on them (a dot on the planet, a count on the Dock or taskbar icon unless turned off). These choices are the device's, in `workspaces.json`, and sit in Settings › General with opening at login (`src-tauri/src/open_at_login.rs`): Login Items on macOS through Apple's `SMAppService`, the `Run` key on Windows (both through the `auto-launch` crate) and an XDG autostart entry on Linux (`linux_autostart.rs`). The system's record is the truth, read each time, so turning it off in the system's own settings shows. A launch at login starts with the window hidden, in the Dock or the tray, and shows it where there's no tray to find the app by (on Linux unless a panel registered on the session bus as a tray host, which stock GNOME and a bar without a tray don't); macOS marks such a launch in its launch event (`macos_launch.rs`), the others pass `--autostart`. Only one shyspace runs per person (`single_instance.rs`, Tauri's single-instance plugin): opening it again hands over to the running app, which shows its window, unless that second launch came from a login, and the new process exits. The UI is React in `src/`.

## Core ideas

1. **One workspace = one MLS group.** OpenMLS handles membership and key agreement. MLS is only used to agree on one secret per *epoch* (a period between membership changes). Content is encrypted with a key derived from that secret.
2. **Everything is an op.** Any change (message, reaction, page edit, rename…) is an `Op` (`ops.rs`). The author signs it with their identity key, then it is encrypted with the epoch key (`crypto.rs`). The result is an `Envelope`.
3. **Two ways to deliver, same envelopes.** Envelopes are sent live over iroh gossip and also uploaded to the bucket. A member that was offline catches up from the bucket. Gossip also carries signed presence heartbeats (every 25 s, and when a peer connects), which are never stored. Huddle beacons (who is in which voice huddle) travel the same way for public channels, and straight to each member for private channels and DMs; they are never stored either. Who has a page open, and their cursors, travel on a gossip topic of each page's own, joined only while the page is open (`transport/page_gossip`, `workspace/pages_live`), never stored.
4. **No ordering needed.** Every op merges the same way whatever order it arrives in. That is why two unordered transports are enough:
   - names, titles, channel renames, message edits, file renames, profiles, profile details and statuses: last writer wins, by lamport clock (edits are kept apart from what they change, so an edit may arrive first);
   - deletes: permanent markers that win over everything else about their target; later ops touching a deleted item are dropped;
   - reactions: per-author on/off toggles;
   - page content: Yjs CRDT updates;
   - creations (channel, message, page): the id contains the author's key prefix, so only the author can create or overwrite it.
5. **Local first.** Each device stores ops and the views built from them in SQLite (`storage/`). Reads never touch the network. Search uses SQLite FTS5, on the device, with filters parsed in `search.rs` (`from:`, `in:`, `before:`, `after:`). It indexes the words people see (`markdown.rs`): link and mention names without their addresses, and no markdown marks, HTML, images or bare `shy://` links. Text that reaches the app already cut (search snippets, thread summaries, notifications) is made from what a reader sees, with every app link named by its real target as its chip names it (`markdown::preview_text`): the member's current name, "📄" and the page's title, "💬 a message". A snippet is cut around the first matching word when the search runs, so names are always current.
6. **People, not devices, in what you read.** Ops are stored and applied per device, as they were signed. The views resolve each device to its person (`MESSAGE_PERSON` in `storage/queries.rs`): a message's `author` is the person and its `device` the device that wrote it. A message's place in a channel is its clock and device (two of a person's devices can share a clock), so paging and read positions use the device. "You" is your person (`Workspace::my_id`): what any of your devices wrote raises no alert, counts as read and shows in your sent list. A person's name, status, details and picture are the newest any of their devices set (by clock, then device key), the member list, who's on a page and who's in a huddle show each person once (a person is active, and online, while any of their devices is), as do huddle peers and who is speaking, and a reaction counts once per person: the newest toggle among their devices decides, so any of them can take it back (each device's log keeps its own limit of 20). Signing, new ids, files and sync stay on the device (`Workspace::me`).
7. **Mentions are links in the text** (`mentions.rs`): `[@Ada](shy://member/<id>)`, `[@channel](shy://mention/channel)`, `[@here](shy://mention/here)`. They need no op of their own; each device works out what mentions it, so this works under end-to-end encryption.
8. **Threads are replies** (`storage/threads.rs`): a message with `reply_to` lives in the thread of the message it eventually answers, in the same channel, worked out when reading so arrival order doesn't matter. A reply whose parent is missing shows in the channel. A thread's first message carries a summary of its replies: the count, the latest few distinct repliers, and the last reply's author with a short one-line preview cut in the core. You follow threads you started, replied in or were mentioned in, unless you choose otherwise; their new replies alert you.
9. **Alerts are decided on the device** (`sync/alerts.rs`): a new message from someone else raises `Change::Alert` when that channel's level (all, mentions, or nothing) allows it and it was written in the last 10 minutes, so catching up never floods you. The desktop app shows it unless you're looking at that channel, titled with the person for a DM ("Grace"), the group ("Grace in your group with Alan") or the channel ("Grace in #plans"), with the sender's avatar as its picture where the system shows one (clicking it brings the window forward at that message; see `src-tauri/src/alerts.rs`), and keeps running in the tray when its window is closed. How many things need you (Inbox items, unread DMs you haven't muted, due reminders) shows in the window title, as a taskbar or dock badge where the system has one, and beside the tray icon. On macOS the installed app sends alerts through Apple's notification center (`src-tauri/src/notify_macos.rs`, the crate's one file allowed `unsafe`, for the Objective-C calls), which also tells it whether notifications are allowed (`notification_permission.rs`): it asks once a workspace is open, and Settings › Notifications shows the way back when they're off. Alerts about a message there have Reply and Mark as read buttons, and page mentions only Mark as read (`alert_actions.rs`). A click, or a button's action, waits in the app until the UI takes it (so one that launched the app isn't lost), which writes a reply's mentions as the composer does and sends it where the message is (its thread, or its channel); a reply leaves any draft there as it was, and one that fails becomes the draft there (a message box open on it shows it at once, after anything typed), and another notification says so (with the text, unless notification text is hidden, when even the draft can't be saved). Elsewhere, and in development builds on macOS, alerts go through Tauri's notification plugin, with no buttons.
10. **The inbox** (`workspace/inbox.rs`) gathers unread mentions and new replies in followed threads across channels, from the same read positions, so reading something anywhere clears it. It also lists mentions of you in pages (`workspace/page_mentions.rs`), one per page and author, at the latest.
11. **Page mentions** (`sync/page_mentions.rs`): when someone else's page update inserts a link to you, the device notes it for the inbox (if written in the last 7 days) with its line as written and where it is, as a Yjs relative position that stays put as the page changes, and raises `Change::PageAlert` if it was written in the last 10 minutes and your status allows alerts. Only inserted text counts, read from the update itself (`pages::insertions`), so mentions already on a page count again only if inserted again. @channel and @here mean nothing in a page. Opening the page clears its mentions; a notification or inbox entry opens the page at the mention, or where it was if it's gone.
12. **Personal state stays on the device.** Things only you care about, like where you've read up to in each channel or thread, alert levels, which threads you follow, unsent drafts and unsaved edits of your messages (`workspace/drafts.rs`), what you saved for later (with reminders) and how you group channels into sidebar sections (`storage/reading.rs`), are plain local rows, not ops: nobody else sees them, and they don't sync between devices.

## Identity and local data

Each member has an iroh ed25519 key. It is their network address, signs their ops, and is their MLS credential identity. Their MLS signature key is a separate key, bound to the identity by a signature (`mls::binding_message`).

A *device* is one identity key, with its own log and MLS leaf; a *person* is who the app shows. A person's id is their first device's key, so without linked devices the two are the same. Another device belongs to a person through a certificate that the device and one of the person's devices sign (`membership/device.rs`). The certificate travels in the commit that adds the device, and every member records the ones that count in the `devices` table (`storage/devices.rs`). Tables stay keyed by the device that wrote; rights look up its person as of the epoch an op was sealed in, and views by the current map, which gives the same answer since a device writes only from the epoch it was linked at. Positions that order things (a lamport clock plus a key) stay on the device.

A member's data directory holds two SQLCipher-encrypted databases (`shy.db`, `mls.db`) and a `workspace.json` with only non-secret settings (workspace id, name, admin). The identity key and bucket credentials live inside `shy.db`. Both databases are encrypted with keys derived from a random *device key* (`keys.rs`), kept outside the directory: in the OS keychain, in a key file (`shy --key-file`) on servers, or, in the phone apps, in a store the app provides (`keys::HostKeyStore`, backed by the iOS Keychain or the Android Keystore), one account per workspace.

The desktop app holds every workspace on the device (`workspaces/`): each in its own data directory, `workspaces/<workspace id>/`, with its own device key, identity and connections, so two workspaces share nothing and can't tell they share a person. `workspaces.json` beside them keeps only this device's choices (`device_settings.rs`): their order, which were used last, which are muted, a pause on notifications, and the microphone, speaker and join/leave sounds huddles use, whichever workspace calls (a choice a workspace kept itself, from before, becomes the device's the first time it has none). A workspace id names a folder and comes from invites and recovery kits, so only plain names are accepted. All workspaces stay open, gossip delivering live to each; the five used most recently also check the bucket at the normal pace, the rest every five minutes (`sync::Cadence`), so in those a silent gossip split can go unnoticed for that long. Leaving a workspace closes it, then deletes its folder and its device key; if the folder is still in use, leaving fails and the workspace stays, closed until it is opened again. A file or folder there that isn't a readable workspace is skipped, and an unreadable `workspaces.json` is reported and ignored, so neither stops the others opening. Most commands act on the selected workspace; what belongs to the person or the device acts across them: the one call the device can be in (joining one leaves any other, and it can be muted or left with another workspace shown), a ring from any workspace, being away, and reminders that come due. A device with the single folder of earlier versions has it moved into this layout once on start: the device key is stored under the new folder's name first, then the folder renamed, then the old key forgotten, so a move cut short finishes the next time.

## Membership

Only the admin (the workspace creator) changes membership. This keeps a single, linear chain of epochs without needing a server to order commits.

- **Inviting:** the admin creates an invite (`membership/invite.rs`). Its code is single-use, expires after 7 days, and holds the workspace id, the admin's keys, a token, the admin's public key for this invite's join request, and two presigned links: one to upload a join request, one to download the answer. It contains no bucket credentials.
- **Joining:** the joiner posts their key package, identity binding and name through the request link, sealed to the admin (`membership/request_seal.rs`). The admin's app shows the request; the admin approves or declines. On approval it signs and saves the commit, applies it, and answers with the MLS Welcome plus an encrypted *grant*: the key history (older epoch keys, their members, removed members' frozen logs) and the bucket credentials. The answer goes up once and again every 10 minutes (in case it was removed) until the newcomer posts or is removed, then it is deleted. The joiner can cancel while waiting (`JoinCancel`); a cancel only counts before the answer arrives, so a join is never left half done, and the request stays in the admin's list until declined or expired. Asking again from the same device keeps that first request (and its name); its key package's secret is still on the device, so approving it lets the device in.
- **Recovery:** the admin can export a *recovery kit* (a code holding a random recovery key and the bucket settings). After every membership change, the admin's app uploads an encrypted snapshot of its admin state (MLS state, identity, keys, members, commits, invites, settings, and the admin's sidebar sections with the channels in each) to `recovery/snapshot`. It holds no content: messages, pages, files and pictures come back from the bucket, and personal state (read positions, drafts, Later) stays behind; `storage/snapshot.rs` lists every table as kept or left out. A snapshot larger than restore reads (32 MB) isn't uploaded, so it can't hold back the membership change; the kit then refuses to restore, as its snapshot is stale, and asking for a new kit fails with an error until the snapshot fits again. The storage settings carry the last snapshot's size and that limit (`recovery_snapshot_bytes`, `recovery_snapshot_limit`), so the app can warn early. `restore` on a new device decrypts it, then re-downloads everything else from the bucket, including the admin's own log so its sequence numbers continue. See `membership/recovery.rs`.
- **Storage settings:** the admin can change the bucket's region and keys (`workspace/storage.rs`). The change is an op like any other, so it reaches members live or through the bucket; each member stores it and reconnects. A member offline while the old key was deleted asks another member for the settings instead (`sync/key_handoff.rs`). The endpoint and bucket can't change: the data would stay behind.
- **Removing:** the admin pulls the member's latest ops, then commits the removal with their last sequence number. The new epoch's key never reaches them, and later ops from them are rejected. Removing a person removes all their devices in one commit, each log frozen at its own last op (`remove_member`); removing devices (`remove_devices`, say a stolen phone) leaves the person their other devices.
- **Linking a device:** the new device learns the workspace from one of the person's devices, makes its key and signs that it belongs to the person, and that device vouches for it. The admin's app runs every check members run on the certificate and commits the add with it (`membership/admin.rs`, `add_device`). The device then joins as a newcomer does and reads the commit that added it, to count its own certificate (`workspace/enrollment.rs`). A person has at most 5 devices among the current members. The two devices meet through a link code the person's device shows (`workspace/linking.rs`): the new device posts a request through it, the person taps, on the device they already use, the number the new device shows, and that device vouches, asks the admin's app to add the new one (a device change op) and hands it what a newcomer's grant holds, up to now. The new device reads at once from that, in a store of its own that can't write to the bucket (`workspace/device_linking.rs`, `workspace/reading.rs`), and joins in its real folder once the admin's app adds it. Until then, the device that confirmed it finishes, retries or cancels the link after each sync pass (`workspace/link_tending.rs`). A person sees their devices and asks to remove them from any of them (`workspace/my_devices.rs`).
- **Commits** are wrapped in the admin's signature (`SignedCommit`). Members ignore anything else in a commit slot. Once the workspace has a linked device, every commit uses the v3 wrapper: it carries the device certificates, sealed with the key of the epoch it leaves, and a format and rules number, so an app too old for either asks for an update (`membership/commit.rs`). The admin re-uploads its commits if they go missing or are altered.

## Sync loop (`sync/`)

Bucket requests cost money on some providers, so the loop reads as little as it can (#137). After each upload an author rewrites their head (`heads/<id>`, the last seq they uploaded) and gossips a signed hint naming the head's version (`sync/heads.rs`). Most passes are *checks*: one listing of `heads/` (heads of keys that were never members are ignored), and only the logs whose head moved in a way no hint explained are read; removed members whose frozen log we haven't finished (again only once something new of theirs came), and authors with a gap, are read past what we hold. A head counts as seen only once its log was read, so a failed read is retried at the next check. A *sweep* reads every author's log past what we hold: at start, after the computer slept, and at least hourly by the saved wall clock (at once if the clock was set back). Checks wait 8 s after one that found something gossip missed, then half as long again after each empty one, up to a minute (`sync/pacing.rs`); a hint naming ops we lack, an admin's commit nudge, or a neighbour joining wakes one at once, and the admin looks at open invites' request slots every 8 s, since joiners can't nudge. Our own writes don't wake a pass: a separate task uploads them 600 ms later, then writes our head and sends the hint. Each step of a pass runs even if another fails:

1. apply new admin commits (advance epochs);
2. retry parked ops;
3. admin only: refresh the recovery snapshot, then collect join requests and deliver answers;
4. every 10 minutes and at sweeps: repair missing or altered commits (one listing of `mls/commit/`; only slots whose version changed since we found them right are fetched) and learn the forks proved in the bucket, putting there the proofs we have that it lacks (`sync/forks.rs`);
5. read new segments: the logs whose heads moved (a check) or everyone who was ever a member, ourselves included (a sweep; newcomers need removed members' history, a restored device its own);
6. push our unpushed ops as segments, each under the 32 MB that readers accept, then any packs due (below);
7. relay others' ops the bucket still lacks a while after they reached us live (`sync/relay.rs`): their device may have died before uploading. We go once the members online whose keys are closer to the author's have had their turn (2 minutes, then a minute each), after looking in the bucket, so usually one member uploads them;
8. refresh the gossip allowlist to current members; every 10 minutes, connect to members listed in the bucket.

A check lists an author's segments past the highest seq we hold; a sweep lists past what it has checked against the bucket, so ops that came only over gossip are compared with the bucket's copy (a segment whose range we hold is fetched only if its name's hash differs from our own copy's). Either first fetches the covering chain: from what we hold, the object that reaches furthest (the narrower on a tie), then again from its end (`sync/packing.rs`); then it fetches the rest that may hold more a few at a time, and applies a segment's ops in transactions of up to 500, letting go of the state between them (each op still on its own). Uploads never overlap; a failed one is retried by the next check.

An incoming op is applied only if it decrypts, its signature is valid, its author was a member in that op's epoch, and it directly follows that author's previous op (logs have no gaps). Ops we can't apply yet (unknown epoch, clock far ahead) are parked in `pending_ops` and retried. If a second, different version of an op we already have arrives, signed by its author, neither version counts (see Forked logs in `security.md`).

## Bucket layout

Everything is under a `<workspace id>/` prefix. Only ciphertext and public ids are stored.

| Path | Content |
|---|---|
| `ops/<author>/<last seq>-<first seq>-<nonce>-<hash>` | a segment of that author's envelopes, written create-only; the name leads with the last seq so a reader lists exactly what holds more than it has, holds a random nonce picked at upload so nobody can take the name first, and ends in a BLAKE3 hash of the nonce and the bytes. Packs are segments too: when an author has pushed through a multiple of 16, 256 or 4096 ops, they upload that aligned range again as one object (if it fits), so a reader catching up fetches a few wide objects rather than one per upload. Usually written by the author; any member may relay the author's own signed ops there when the author's upload never came, and readers check every op either way |
| `ops/forks/<author>/<seq>/<hash>` | proof that the author signed two versions of that op: both envelopes |
| `mls/commit/<from epoch>` | admin-signed MLS commits; any member puts one back within 10 minutes if its slot goes missing or holds something else |
| `invites/<token>/request` | a joiner's request, sealed to the admin, written through a presigned link |
| `invites/<token>/answer` | the admin's answer, read through a presigned link |
| `links/<token>/request` | a new device's link request, sealed to the link code's key, written through a presigned link |
| `links/<token>/answer` | the voucher's signed check, then the hand-over in its place, read through a presigned link |
| `links/<token>/<device>/welcome`, `links/<token>/<device>/outcome` | the admin's signed welcome for a device it added from a link, or its signed refusal; kept 7 days |
| `recovery/snapshot` | the admin's recovery snapshot, encrypted with the recovery key |
| `heads/<id>` | the last seq that member uploaded and a short tag of the bucket key they use, rewritten after each upload and after the key changes; a hint only (`transport/heads.rs`) |
| `peers/<id>` | gossip bootstrap hints, rewritten when a member starts and every 6 hours; members silent for a day aren't dialed, and nobody is redialed more often than every 10 minutes unless they announce again (`sync/peers.rs`) |
| `files/<author>/<blob id>/<piece>` | a shared file's or profile picture's encrypted pieces (`transport/blobs.rs`) |
| `health/versioning-probe`, `ops/lock-probe-<member>` | small probes that prove the bucket keeps deleted data (see `workspace/protection.rs`) |

## Pages

A page is markdown in one Yjs text named `content` (`pages/`). The desktop editor (CodeMirror + `y-codemirror.next`) and agents (Rust `yrs`) edit the same structure. Agent edits change only the part that differs, so they don't clash with people typing nearby. Every edit is written as a Yjs client bound to its author: each editor session, and each agent edit, gets a random nonce, its client id is a hash of the author, page and nonce (`pages::client_id`), and the `DocUpdate` op carries the nonce, so every device can check that the update only adds pieces for that id. Page updates applied in one transaction (a downloaded batch of up to 500 ops) are merged in memory and each page is written and reindexed once when it commits (`storage/page_cache.rs`), so catching up on hours of typing costs the size of each keystroke, not the whole page each time; a savepoint that rolls back takes back what it merged. A page shared in chat (`shy://page/<id>`) shows as a live card. In a page, links to messages (`shy://message/<id>`) show as chips that open the message. The editor shows the markdown as live preview (`features/pages/editor/`, rules in `design-system.md`); what is stored stays plain markdown.

## Files and profile pictures

A shared file is a `File` op (`files/`): its own id (owned by its author, like a message), the place it was shared in, the message it came with, a cleaned name and media type, and a reference to its encrypted bytes (a *blob*). The blob has a random key and is sealed in 4 MiB pieces (`files/blob.rs`); the reference holds the key and a hash of every sealed piece. The sender seals the file into its local cache, uploads the pieces, and only then writes the op, so an op always means its pieces are in the bucket (`workspace/files.rs`). In a private channel or DM the op is sealed like any content there. Others fetch pieces only when they open a file, check each against its hash, and keep them, still encrypted, in a cache of up to 2 GB that drops what was opened longest ago (`files/cache.rs`). Plaintext leaves only through "Save as" or, for showing, memory.

The admin can give the workspace an icon and a default theme and accent (`workspace/look.rs`): a `WorkspaceIcon` op, stored and replaced like a profile picture, and a `WorkspaceLook` op holding two names the app maps to its themes. Members see them as defaults and can still choose their own look on their device. The rail shows each workspace's icon by its id (`WorkspaceItem::icon`), which changes with the picture.

A file can also be shared into a page: then its place is the page and it has no message, the page loads only its own files, and its changes come as `Change::PageFiles`. Deleting a file, its message, its channel or its page removes it everywhere and queues its blob for removal (`storage/files.rs`); the device that deleted it takes the pieces out of the bucket on its next sync pass, and every device drops its cached copy. A profile picture is a `ProfilePicture` op pointing to a small blob (at most 512 KB, PNG, JPEG or WebP), the latest wins, and the one it replaces leaves the bucket the same way. Pictures are cached apart and never dropped.

## Database schema

Stored data is kept from v0.1.0 on. `storage/schema.rs` holds the schema as a list of migrations, and a store's `user_version` is how many it has had: an older store takes the rest when it opens, and one from a newer app is refused with "update shyspace". A `user_version` above 1,000 or below zero is no count but the mark of a build that never shipped, and is refused with "create it again", since no update reads it. A change is a new, additive migration at the end. The rules that build views from ops have their own number (`VIEW_RULES`, kept in `meta`); a store whose views were built under older rules has them rebuilt from its log when it opens, and one built under newer rules is refused with "update shyspace", as rebuilding would meet ops this version can't read. The op format (`crypto::OP_FORMAT`) isn't part of either: newer ops wait for the update, and a new format must keep reading every older one, since logs keep them. Each version records the op format it reads in `meta` when it opens a store, and a store a newer format has been recorded in is refused the same way, since its log may hold ops this version can't read.
