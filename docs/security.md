# Security

What shyspace protects, how, and where it falls short. Update this whenever a change touches crypto, membership, sync or what the bucket stores.

## Who we defend against

| Who | Can | Cannot |
|---|---|---|
| The bucket provider, or anyone who reads the bucket | see metadata (who writes, how much, when) | read or forge content |
| Anyone with the bucket credentials (every member) | delete data, disrupt sync | read or forge content, join without the admin |
| Anyone holding an invite code | ask to join once, before it expires | get in without the admin's approval, touch anything else in the bucket |
| A removed member | read what they already had | read anything written after removal |
| A current member | write as themselves | write as someone else, take over others' messages, change membership |
| Someone who copies a member's data directory | nothing, without the device key | read messages, keys or credentials |

## Defenses, and where they live

- **Content encryption:** sign-then-encrypt with XChaCha20-Poly1305. The signature and the AEAD both cover the header (author, seq, epoch). See `crypto.rs`.
- **Per-epoch keys** come from the MLS exporter. A removal starts a new epoch. See `mls.rs`.
- **Author must belong to the op's epoch:** checked in `sync.rs` (`verify`) against `epoch_members`.
- **Gap-free logs:** an author's op applies only right after their previous one, so a log has no holes to fill later. A verified op that breaks a rule (someone else's id, an admin-only change, a damaged page update) is recorded as handled and skipped, so it can't block what follows. Other failures, like a full disk, are retried instead. See `sync/receive.rs`.
- **Removed members' logs are frozen:** before removing someone, the admin pulls their latest ops and puts their last sequence number in the signed removal commit. Every member (and every later newcomer, through the key history) rejects ops from them past that number. A device that already applied some of those (sent live just before the removal reached it) takes them out of its log and rebuilds its views from the rest, so every device ends up the same. Page edits someone made on top of those late edits can't apply anywhere and are lost. See `membership/admin.rs`, `sync/receive.rs`, `storage/rebuild.rs`.
- **Owned ids:** a channel, message or page id starts with its creator's key prefix (16 bytes), so nobody else can claim it. See `ops.rs` and `store.rs`.
- **Who may change what:** only a message's author may edit it; only an item's owner or the admin may delete a message, channel or page. Ownership comes from the id, so every member checks this the same way, in any order. Forged edits and deletes are skipped like any other rule-breaking op. One `Delete` op removes whatever its id names, and deleting a channel also marks its messages deleted, so no arrival order can bring anything back. See `Op::is_permitted` in `ops.rs` and `storage/revisions.rs`.
- **Channel names:** renames from anyone must be 1–80 letters, digits, dashes, dots or underscores, or they are skipped. Created names (which older versions allowed to be anything) are kept but cleaned the same way on every device: control and invisible characters dropped, cut to 80 characters. So nothing in the sidebar can be disguised.
- **Size limits:** messages and edits hold at most 40,000 characters and page titles 200, so nobody can push megabytes into everyone's view and search index. Your own longer text is refused. Longer text from others is cut to the limit rather than skipped, the same way on every device, so devices from before the limit (which show it whole) and after it still agree that the message exists, and the author's later ops aren't held up. Text that arrived before the limit existed stays as it was. See `MAX_MESSAGE_CHARS` in `ops.rs`.
- **One message per id:** an author's ops apply in the same order everywhere, so the first message with an id wins and later ones with the same id are ignored. A message posted into a deleted channel is marked deleted too, so it can't reappear elsewhere.
- **Ops from newer versions:** a validly signed op whose kind of change this version doesn't know waits with the parked ops instead of being dropped, and applies after an update. The app asks the user to update only when such an op is the next one its author needs, so a junk op far ahead can't raise a false alarm. See `crypto::NewerFormat`.
- **Gap repair:** parked ops are capped, so one can be pushed out after we've read past it in the bucket. When an author's next op is missing from the parked ones, we read that author's segments again (once per gap per run). See `sync/replicate.rs`.
- **What delete promises:** deleted content disappears from every member's app and search, and each device removes it from its views. The encrypted op that created it stays in the log (members need the log to sync), so a member who synced before the delete still holds it, and could dig it out. Delete is for tidying and moderation, not for recalling a secret: rotate the secret instead.
- **Clock bound:** ops whose lamport clock jumps more than 2^32 ahead wait instead of applying, so one op can't pin titles forever.
- **Junk can't shadow real ops:** ops are stored only after they verify. Parked ops get one row each, keyed by hash, capped per author and in total.
- **Commits are admin-signed;** members ignore anything else. The admin saves a commit before applying it. Every member keeps the commits it applied and re-uploads any that go missing or change in the bucket.
- **Invites:** single-use, expire after 7 days, need the admin's approval, and carry only presigned links (no credentials). The joiner sees a 20-digit safety code derived from their key; the admin sees the requester's code and should compare it out of band before approving, since a leaked code lets someone else ask in the joiner's name. Credentials reach the newcomer only inside the MLS-encrypted answer. See `membership/admin.rs`.
- **Identity binding:** a joiner's key package must be signed by the identity it claims. The invite pins the admin's MLS key, so a forged Welcome is rejected.
- **Members-only gossip:** peers that aren't current MLS members are refused at connection time, and we only dial members. See `transport/gossip.rs`.
- **Presence:** "online" and "away" travel only as heartbeats over members-only gossip, never through the bucket, and are kept in memory only. Each heartbeat is signed by the member's identity key for this workspace and carries its send time; heartbeats that are badly signed, more than 2 minutes off, or from someone who isn't a current member are ignored, and a member's presence can change at most once a second, so nobody can make everyone's member list redraw nonstop. We send at most one heartbeat every 5 seconds unless our own state changed (one held back goes out when the 5 seconds end), so a peer reconnecting over and over can't make us sign nonstop. Without one for 75 s a member shows as "not reachable". Presence tells other members when you have the app open; **Appear offline** stops sending heartbeats. It is saved in the encrypted database and read before the first heartbeat, so a restart never announces you. Turning it on sends nothing, so others keep seeing you online until your last heartbeat expires (up to 75 s). See `workspace/presence.rs`.
- **Status:** a status (emoji, up to 100 characters, an end time, which alerts you want meanwhile) is an ordinary op, so only its author can set it. Longer ones, or ones with control characters, line breaks, or invisible characters that hide or reorder text (like right-to-left overrides), are skipped, so a status can't disguise the name beside it. Its alert level only quiets your own notifications, and never makes a muted channel louder; it isn't enforced on others.
- **Admin recovery:** the recovery kit is a secret (recovery key plus bucket credentials). Snapshots in the bucket are encrypted with a key derived from the recovery key and bound to the workspace id. A snapshot is always uploaded before the commits it covers, and restore refuses a snapshot when the bucket holds any admin-signed commit from the snapshot's epoch onward (a rolled-back or stale snapshot). Deleting those slots doesn't help: members re-upload them. A failed restore removes only what it created. See `membership/recovery.rs`.
- **Storage settings:** only the admin can change the bucket region and keys. New settings are checked against the bucket first, travel as an admin-only op encrypted with the current epoch key (so removed members can't read them), and ops claiming to change settings from anyone else are skipped. Newcomers get the settings with their version, so older changes replayed later can't put back revoked keys. The recovery kit holds the keys too, so after a change the app shows the admin a new kit; older kits stop working once the old key is deleted. Plain `http://` endpoints are refused unless the server is on the local network. See `workspace/storage.rs`.
- **Desktop notifications show message text** to the operating system's notification center, outside the app's encrypted storage. Settings → Notifications can hide the text, leaving only who wrote and where.
- **Personal state isn't shared:** read positions, alert levels, drafts and saved-for-later items never leave the device (drafts sit in the encrypted database, not browser storage) and aren't in the admin's recovery snapshot, so other members (and the bucket) can't see what you've read.
- **Encryption at rest:** both local databases use SQLCipher with keys derived from a device key kept in the OS keychain (or a key file the user places elsewhere). The identity key and bucket credentials are inside the encrypted database; `workspace.json` holds only public settings. See `keys.rs`, `storage/mod.rs`.
- **Chat rendering:** messages become React elements through react-markdown, never HTML: raw HTML and images are dropped, and only http(s), mailto and `shy://` page, message and mention links survive (`lib/markdown.tsx`). External links show their full address on hover, ask before opening when their text shows a different address than they open, and open in the system browser.

## Known gaps

- Bucket credentials are shared by all members, so any member can cause denial of service, or delete the workspace's data unless the bucket keeps it. A retention lock on the write-once `ops/` and `mls/` (Cloudflare R2 bucket locks, S3 Object Lock) stops even someone with the keys; versioning (S3, Backblaze B2, MinIO) undoes accidents, but the shared keys can delete old versions too unless the provider's key rules forbid it. The admin's recovery snapshot (`recovery/snapshot`) is overwritten, so it can't sit under a lock; keep the recovery kit and a working admin device. The app proves which protection holds, daily, by writing small probes (`health/versioning-probe`, `ops/lock-probe-<member>`), and Settings warns until it's locked (`workspace/protection.rs`, #83). It can't tell S3 Object Lock from plain versioning, so it reports that as versioned.
- Single admin. A recovery kit restores a lost admin device, but there is still only one admin at a time; restoring while the old device is alive would cause conflicting membership changes (#5).

Issues labeled `security` track these: <https://github.com/shynewt/shyspace/issues?q=label%3Asecurity>

- A restored admin can reuse sequence numbers of ops that reached peers only live before the old device died (#26).
- A removed member's open gossip connection stays up until it drops; they see traffic timing, not content (#27).
