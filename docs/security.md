# Security

What shyspace protects, how, and where it falls short. Update this whenever a change touches crypto, membership, sync or what the bucket stores.

## Who we defend against

| Who | Can | Cannot |
|---|---|---|
| The bucket provider, or anyone who reads the bucket | see metadata (who writes, how much, when) | read or forge content |
| Anyone with the bucket credentials (every member) | delete data, disrupt sync | read or forge content, join without the admin |
| Anyone holding an invite code | ask to join once, before it expires | get in without the admin's approval, touch anything else in the bucket |
| A removed member | read what they already had | read anything written after removal |
| A current member | write as themselves | write as someone else, take over others' messages, change membership |
| Someone who copies a member's data directory | nothing, without the device key | read messages, keys or credentials |

## Defenses, and where they live

- **Content encryption:** sign-then-encrypt with XChaCha20-Poly1305. The signature and the AEAD both cover the header (author, seq, epoch). See `crypto.rs`.
- **Per-epoch keys** come from the MLS exporter. A removal starts a new epoch. See `membership/mls.rs`.
- **Author must belong to the op's epoch:** checked in `sync/receive.rs` (`verify`) against `epoch_members`.
- **Gap-free logs:** an author's op applies only right after their previous one, so a log has no holes to fill later. A verified op that breaks a rule (someone else's id, an admin-only change, a damaged page update) is recorded as handled and skipped, so it can't block what follows. Other failures, like a full disk, keep the op parked on this device: it is tried again on every sync, and the error shows until it applies. A number from someone else too large for the store (a key generation, a sequence or position in a private op) is a broken rule, never a local failure, so it can't hold up its author or leave a lasting error. See `sync/receive.rs`.
- **Removed members' logs are frozen:** before removing someone, the admin pulls their latest ops and puts their last sequence number in the signed removal commit. Every member (and every later newcomer, through the key history) rejects ops from them past that number. A device that already applied some of those (sent live just before the removal reached it) takes them out of its log and rebuilds its views from the rest, so every device ends up the same. Page edits someone made on top of those late edits can't apply anywhere and are lost. See `membership/admin.rs`, `sync/receive.rs`, `storage/rebuild.rs`. A removed member's frozen log end in the admin's commit that is past anything the store holds freezes nothing more (no op has such a number), so it can't stop members following commits.
- **Owned ids:** a channel, message or page id starts with its creator's key prefix (16 bytes), so nobody else can claim it. See `ops.rs` and `storage/apply.rs`.
- **Who may change what:** only a message's author may edit it; only an item's owner or the admin may delete a message, channel or page. Ownership comes from the id, so every member checks this the same way, in any order. Forged edits and deletes are skipped like any other rule-breaking op. One `Delete` op removes whatever its id names, and deleting a channel also marks its messages deleted, so no arrival order can bring anything back. See `Op::is_permitted` in `ops.rs` and `storage/revisions.rs`.
- **Channel names:** names from anyone, created or renamed, must be 1–80 letters, digits, dashes, dots or underscores, or the op is skipped on every device. So nothing in the sidebar can be disguised.
- **Page titles:** anyone may rename any page, and titles show in the sidebar, in links and to agents, so titles from others are cleaned like display names (no line breaks, control, invisible, text-direction or tag characters, though the zero-width non-joiner Persian needs stays) and cut to 200 characters on every device; your own app refuses a title it would have to clean. A line break could otherwise fake a quote or a link in every message that links the page. See `clean_page_title` in `ops.rs`.
- **Size limits:** messages and edits hold at most 40,000 characters and page titles 200, so nobody can push megabytes into everyone's view and search index. Your own longer text is refused. Longer text from others is cut to the limit rather than skipped, the same way on every device, so the message still exists everywhere and the author's later ops aren't held up. Display names (80 characters) and reaction emoji (32) are cut the same way and lose control and invisible characters, so no name can disguise another (two members may still pick the same name: where it matters, in member pickers, the confirms to remove someone or hand over a channel, and mentions, the app adds the start of each one's safety code, which comes from their identity key; since a joiner could try keys until theirs starts like a member's, approving a request whose code starts with the same eight digits as a current member's is refused; the admin declines it, and since a declined request leaves no key behind on the joiner's device (only the files a join made go, never anything else in its folder), their next request comes with a new key and code. The admin signs a decline over the workspace, the invite and the requester's key; anyone with the bucket keys can write the answer, so an unsigned or wrong one is ignored rather than making a joiner throw away the key the admin is about to approve. An expired request keeps its key.); an op naming an id over 200 characters (real ones are under about 120) is skipped, except that a reply to such an id shows as a plain message; and only the first 200,000 characters of a page go into the search index. See `MAX_MESSAGE_CHARS` and its neighbors in `ops.rs`.
- **Reactions and status emoji are emoji only:** no letters, digits outside a keycap, spaces or ASCII punctuation, so neither can pose as words next to a name or a message ("✓ approved by admin", "(you)"); every device refuses one that isn't. A member keeps at most 20 different reactions on one message (`MAX_REACTIONS_PER_AUTHOR` in `ops.rs`); their next is refused until they take one back, the same on every device because a member's ops apply in their own order. The app shows 20 reactions per message and the rest on request, so many members together can't make a message slow to draw.
- **Op size limits:** one sealed op may take at most 4 MB if it's a page update (room for a very large paste) and 256 KB otherwise (the longest message in 4-byte characters, or a key grant to the most people, needs about 160 KB). The encryption around an op isn't signed, so an arriving envelope opens only if its content is exactly the standard encoding of what the author signed; otherwise anyone with the epoch key could pad someone's op past the limit to get it refused. A bigger op from someone else is checked (decrypted and its signature verified, so nobody can mark another member's op as handled) and then recorded as handled with only its header kept: its content takes no room and never applies, and the author's later ops aren't held up. One that arrives before its turn isn't kept in full while it waits; gap repair reads it again from the bucket once a later op of its author's is waiting behind it. (If it still isn't ready then, say its clock is implausibly far ahead, that author's later ops wait until the next restart; only a misbehaving author's own log is held up.) An op that can't be checked yet (its epoch key hasn't arrived) waits only if it is within 4 MB. Our own app refuses to write an oversized op, with a clear error; the page editor sends one change at a time and, if one fails, reloads the saved page, so it never builds on a change nobody else has. See `Envelope::fits_size_limit` in `ops.rs`.
- **Page updates:** yrs, which merges pages, trusts what an update says, and crafted updates made it overflow the stack (aborting the app), reserve gigabytes, panic, loop forever or crash. A page is one Yjs text, and an honest editor only appends its own new pieces, so before yrs sees an update from someone else, `pages/update_check.rs` refuses it as a broken rule unless: it holds only text or deleted text on the page's text; each client's pieces come once and start exactly where that client's pieces end on this page (counting ones yrs keeps waiting for what they build on), with no gaps or empty pieces; its deletions are sorted ranges with space between them, at most 100,000 (yrs slows down with each); pieces stay below clock 2^30 (yrs panics past 2^31); and every count fits in the bytes that follow and every number fits what yrs holds. We also run a patched copy of yrs (`vendor/yrs`, #185) in which splitting and joining many small pieces costs memory and time in proportion to their number rather than its square, which one valid-looking update could use to freeze every device or exhaust its memory. yrs still isn't built for hostile input, so this narrows what reaches it rather than proving it safe; see known gaps.
- **Page editor ids (#187):** every page update carries a random 16-byte nonce, and may only add pieces for the Yjs client id `blake3::derive_key("shyspace page client id v1", author ‖ page ‖ nonce)` cut to 53 bits. Each editor session and each agent edit picks a fresh nonce. Every device works the id out from the op, and `pages/update_check.rs` refuses an update that adds pieces for any other client (it may still name anyone's pieces as neighbours and delete anyone's text), so nobody can write under someone else's editor and get their edits refused. The verdict depends only on the op, so arrival order and rebuilds agree. Yjs quietly picks a new client id when a remote update uses the doc's own, so the editor treats a changed id as a failed save and starts a fresh session; it also renews its id daily, once the editor isn't focused.
- **One message per id:** an author's ops apply in the same order everywhere, so the first message with an id wins and later ones with the same id are ignored. A message posted into a deleted channel is marked deleted too, so it can't reappear elsewhere.
- **Reply loops:** a message whose replies loop (a forged client can make one reply to another before it exists) or that sits more than 1,000 replies deep is in no thread: every thread query stops at the same depth, it shows neither in its channel nor in a thread (search and Sent can still list it), it counts for no unread or mention, and replying to it is refused. So it can't break the sidebar, the inbox or links. Threads stay within a channel: a reply to a message in another channel shows in its own channel like any message, and your own app doesn't send one. Messages with the same clock and author, which only a forged op can make, come in id order on every device. See `thread_root` in `storage/threads.rs`.
- **Ops from newer versions:** every op body starts with its format number (`crypto::OP_FORMAT`). A new kind of op keeps the format: an app that predates it skips it as unreadable (below) and goes on with its author's later ops, and once updated rebuilds its views (`storage::VIEW_RULES`), which applies the kept op. A validly signed op in a newer format waits with the parked ops instead of being dropped, and applies after an update; the app asks the user to update only when such an op is the next one its author needs, so one far ahead can't raise a false alarm. A signed op in our own format that doesn't decode (or has no clock) is junk, not a newer version: it is recorded as handled, kept whole but never applied so a second version for that seq is still proved a fork, raises no notice, and doesn't hold up its author's later ops, also when it first waited for its epoch key (`crypto::Unreadable`). A member can still claim a newer format number on junk to raise the notice; the sync status then names whose app sent it (`needs_update_from`), and the sidebar's notice says whose app it was ("Grace's app sent something this version can't read…"), so the admin knows whom to ask or remove. See `crypto::NewerFormat`.
- **Forked logs:** an author could sign two different versions of one op and show each to different people, say one live and one in the bucket. A device that gets a second version of an op it has checks it like any op and compares what the author signed (not the encryption around it, which anyone with the epoch key can redo, so nobody can frame someone with a copy). If they differ, neither version counts on that device, and the views are rebuilt without it. The proof (both versions) goes to the bucket under `ops/forks/`, where every device checks it for itself every 10 minutes and at each sweep, so all devices end up alike; any device holding a proof puts it back if it goes missing. We drop both rather than pick one: a rule for picking would let the author replace an old message everywhere. Proofs about ops past a removed member's frozen log are refused. Each proof in the bucket is fetched once (up to 64 MB, two of the largest segments), or again once the epoch key it needs arrives or the object changes. A proof's name holds its hash, so one overwritten in an unlocked bucket is noticed: devices holding the proof put it back, and readers look at the new version. Someone who keeps overwriting it can keep readers from learning the fork, as they could delete segments; lock `ops/` to stop both. A second version that arrives before its turn is kept and checked, not dropped. Ops we got only over gossip are still compared with the bucket's copy: each sweep (hourly at most) lists an author past what it has checked against the bucket, and a segment whose range we hold is fetched only if its name's hash differs from our own copy's, so a different version there is proved forked within the hour. Limits: someone has to receive both versions, and the author can arrange that nobody does (for example by naming a segment so it sorts before what others have already read); an author can withdraw one of their own old ops this way; a dropped page update can leave later edits that build on it unapplied, the same on every device; and an op refused for its size keeps only its header, so a second version of it can't be compared and is ignored (junk is kept whole up to 4 MB, so it can't hide a fork that way). An honest admin restored from the recovery kit can cause one by accident (#26). See `sync/forks.rs`.
- **Gap repair:** parked ops are capped, so one can be pushed out after we've read past it in the bucket. When an author's next op is missing from the parked ones, we read that author's segments again, at the next check. Only parked ops we could check count: one for an epoch whose key hasn't come could be planted by anyone with the bucket keys, and would otherwise make every new op of that author's fetch their junk objects again (#215). Instead, when a commit brings a new epoch key, the objects skipped as unsettled are read again (junk too, once per key), since ops that waited for that key may settle now; a gap counts as repaired once that read succeeds, so one the bucket can't fill isn't read at every pass and one a network error cut short is tried again. A removed member whose frozen log ends with ops they only sent live, which the bucket never gets, is read again only once something new of theirs came (and at the hourly sweep). See `sync/replicate.rs` and `sync/heads.rs`.
- **Heads and hints:** a member's head (`heads/<id>`) and the hints they gossip only decide *when* a device looks; every op is still verified, and every author is listed again at the next sweep (hourly at most), past what it has checked against the bucket. Hints are signed by their author for this workspace and name a head version; a device skips reading a changed head only if a hint it verified names that exact version and it already holds up to that seq, so replayed or forged hints can't make it skip a head that moved. Heads under keys that were never members are ignored. Anyone with the bucket keys can rewrite or delete a head: one rolled back or deleted delays a reader that missed the gossip until the next sweep (a removed member's log is read up to its frozen end, whatever their head says: at a check once per new op of theirs we hold, and at every sweep); one claiming more than its author wrote costs one listing, and the author corrects it at their next check (after reading their own log, so a restored device never lowers a real head). *Locked buckets:* `heads/` can't be under a lock (it's rewritten), so someone with the keys who keeps overwriting a head can delay a bucket-only reader up to the hourly sweep, where before a lock gave 8 s; forks of ops a reader heard live are then also found at the sweep. See `sync/heads.rs`.
- **Relays:** ops sent live reach the members online at once and the bucket a moment later, so a device that dies in between leaves ops nobody else could ever read again, and a restored admin would reuse their seqs, which every device would prove a fork (#26). So a member holding ops of an author that the bucket still lacks a couple of minutes later uploads them under that author's prefix. Only ops it verified and applied, byte for byte as signed, never parked ones or ones kept as headers, so a relay can't forge or change anything. What the bucket has is taken from the author's signed hints, our checked mark, segments we read from it that continue what we knew it had (a later op read from the bucket says nothing about live-only ones before it), and names starting past that whose hash matches our own copy; never from the unsigned head, which anyone could raise to stop relays, nor from junk names. Members go in turn by how close their key is to the author's, among those online, and look first, so usually one uploads; each relays an author's range once per run, and a relay that fails waits its turn again.
- **Packs:** an author's packs are ordinary segments holding a wider range of their log (16, 256 or 4096 ops), so the rules above and below apply to them unchanged: every op in one is checked on its own, a pack that differs from what we hold is fetched and any second version proved a fork, and nothing is overwritten. A reader tries the covering chain first (the object reaching furthest from what it holds), so anyone with the bucket keys can plant names claiming a wide range to be tried before the honest packs. Each costs one download (at most 32 MB) and is then skipped like other junk; after three such failures for an author in one read, the chain is given up and the rest is read in listing order, several at a time, where names claiming wide ranges sort last, so they can't hold up the honest history. That read takes objects that narrower ones cover (honest packs over their segments) last, each only if what came before left it still holding ops we lack, so a few planted names can't make a reader download the log several times over. Names only order the reading: junk named as narrower segments can't make an honest object be left out. In a sweep, a covered object left unread is still compared with our copy by its name's hash, so a second version kept only in a pack is fetched and proved a fork. A pack is best effort: one the bucket refuses is reported once and not tried again, since readers fall back to the narrower packs and segments it would have covered. Packs group ops by author only, as segments do, so they show the bucket nothing new.
- **Where reading resumes:** anyone with the bucket keys can put objects among an author's segments, and envelope headers (author, seq) aren't signed. So a device never resumes from a bucket key: it lists each author's segments past the highest seq it holds of their log (segment names lead with their last seq), and reads every one that may hold more. Junk, forged headers, or real ops copied under any name are checked op by op and can only add ops that verify; they can't hide any (#208, #209). A name ending in a hash whose bytes don't match is ignored. Objects that don't hold exactly our log are fetched once per run, not on every pass (up to 10,000 remembered, by name and version, so a real upload that replaces junk is read); gap repair fetches them again if their ops went missing. Only names that parse are fetched (past what we hold, or in a sweep a range we hold whose hash differs from our copy's); a segment counts as checked against the bucket only if every envelope in it is the op in our log (the same bytes or the same signed body, since anyone with the epoch key can encrypt an op again) or a proved fork, so junk with real headers can't move that mark; junk costs a line in a listing. See `sync/replicate.rs` and `sync/receive.rs`.
- **What delete promises:** deleted content disappears from every member's app and search, and each device removes it from its views. The encrypted op that created it stays in the log (members need the log to sync), so a member who synced before the delete still holds it, and could dig it out. Delete is for tidying and moderation, not for recalling a secret: rotate the secret instead.
- **Clock bound:** ops whose lamport clock jumps more than 2^32 ahead wait instead of applying, so one op can't pin titles forever.
- **Author times:** an op's time comes from its author's clock. A message, channel, page or file never shows a time later than this device got it, so nobody can date something ahead; backdating only moves the author's own item. Lists of channels, pages and files keep the order ops were made in (their clocks), not the claimed times. A device whose own clock is wrong shows others' items at its own (wrong) time, and a rebuild can show an item at a claimed time that has since passed; times are for reading, never for deciding anything. See `shown_time` in `storage/apply.rs`.
- **Junk can't shadow real ops:** ops are stored only after they verify. Parked ops get one row each, keyed by hash, capped per author and in total.
- **Objects that can't be fetched:** anyone with the bucket keys can put an object a plain GET is refused (with a customer encryption key, or in an archive storage class). A segment like that doesn't stop the rest of the log being read, and is never counted as checked. If its name claims ops past what we then hold, the read counts as unfinished, so the head isn't marked read, the sweep isn't marked done, and a restore (which needs every log read in full) fails rather than going on without it. A removal reads only the removed member's log, giving what was given up earlier fresh tries and reading again (up to 3 times, a second apart) while a download fails, so a network blip can't cut their last messages off on every device; an object that still can't be downloaded is left out, freezing their log at what could be read, since they could plant a fresh one before every attempt and what nobody can read is their own loss. Each object they planted costs the removal up to 3 downloads. At its third failed download in one run it is given up like junk, also through gap repair, so planted objects can't cost a download on every pass or keep reads from finishing. Failure counts (for segments and fork proofs together) are capped at 10,000 objects; past that, as after someone with the keys planted that many, a failed download is given up at once, which they could equally cause by deleting the segment. A head like that means the author's log is read anyway (settling that version of the head once the read is complete), and one log that fails to read doesn't stop the others. A fork proof that can't be fetched doesn't stop the others being learned, and is given up the same way. Our own head, our fork proofs and admin commits that can't be read back are written over rather than compared, so an unreadable commit slot, put right after a removal to keep offline members from following, is repaired like a missing one.
- **Commits are admin-signed;** members ignore anything else. The admin saves a commit before applying it. Every member keeps the commits it applied and re-uploads any that go missing or change in the bucket.
- **Invites:** single-use, expire after 7 days, need the admin's approval, and carry only presigned links (no credentials). The joiner sees a 20-digit safety code derived from their key; the admin sees the requester's code and should compare it out of band before approving, since a leaked code lets someone else ask in the joiner's name. Credentials reach the newcomer only inside the MLS-encrypted answer. See `membership/admin.rs`.
- **Identity binding:** a joiner's key package must be signed by the identity it claims. The invite pins the admin's MLS key, so a forged Welcome is rejected.
- **Members-only gossip:** only current MLS members may be connected to us, in either direction: anyone else is refused once the connection's handshake proves who they are, and we never dial them. When a member is removed, each other member closes their open connections at the sync round where it applies the removal. Gossip relays through any link still open, so the removed member can see the timing of live traffic (never its content) until the last member online has synced. See `transport/gossip.rs`.
- **Presence:** "online" and "away" travel only as heartbeats over members-only gossip, never through the bucket, and are kept in memory only. Each heartbeat is signed by the member's identity key for this workspace and carries its send time; heartbeats that are badly signed, more than 2 minutes off, or from someone who isn't a current member are ignored, and a member's presence can change at most once a second, so nobody can make everyone's member list redraw nonstop. We send at most one heartbeat every 5 seconds unless our own state changed (one held back goes out when the 5 seconds end), so a peer reconnecting over and over can't make us sign nonstop. Without one for 75 s a member shows as "not reachable". Presence tells other members when you have the app open; **Appear offline** stops sending heartbeats. It is saved in the encrypted database and read before the first heartbeat, so a restart never announces you. Turning it on sends nothing, so others keep seeing you online until your last heartbeat expires (up to 75 s). See `workspace/presence.rs`.
- **Huddles:** who is in a huddle travels only as signed beacons, kept in memory and never stored or uploaded. A beacon is signed by the member's identity key over the workspace id, its channel, a random session id and a counter, and is refused if it's from outside the clock skew, older than one already heard in its session, from a session that ended, or from someone who may not be in that channel's huddle right now (a current member of the workspace and, for a private channel or DM, of the channel). A public channel's beacons go over members-only gossip and are refused if sent straight to a device (so nobody can show a public huddle to some members only); a private channel's or DM's go straight to each of its members (`transport/direct.rs`: one message per connection the same members-only hooks admit, read within 5 s, at most 64 at once and 4 per sending device, and confirmed by the receiver) and are refused if they arrive over gossip or from another device than they name. What one device keeps per sender is bounded (one live session, 16 ended ones; a session whose refreshes stop is hidden after 90 s and kept for 4½ minutes, so a later refresh brings the person back after a dropped network, and then forgotten, by when every beacon heard before fails the clock skew check), and visible changes (joining, camera, screen) are limited to a burst of 4, then one a second; changes over that wait for a later refresh. Each device offers its audio only to the verified participants who may be in the huddle, rechecked whenever membership changes and every few seconds, so a removed member drops out of the call. The audio layer (`crates/shy-media`) enforces the same list a second time: each workspace has its own media node on its own endpoint, with its own list, and it admits a session only from a listed peer, who may read only this call's path and publish only at its own, so no one can stand in for another device; anyone else's session is closed, and a peer taken off the list, or everyone when the call stops, is cut off at once. The microphone is encoded as it's spoken: raw audio isn't held back for later listeners (moq-audio's `retain` is off, since it would encode up to 30 s of the past for a new listener), and the encoded track keeps at most 200 ms for a listener that falls behind, so someone let in later can get at most that much from before, never what was said earlier. Paths are random per join, so a peer listed at this device's own path or at another peer's (a session id copied from a beacon) is neither played nor let in, and each peer is read only through its own session, so no device can be played as another. Audio is published at a path derived from the device's key and a fresh random session id (`beacon::media_path_name`), so it reveals no channel or person and can't be reused after leaving; every device derives it from the verified beacon, so a session id copied into another device's beacon leads to that device's own path, whichever beacon arrives first. A device that slept (half a minute or more) leaves its huddle within a second of waking, so its microphone doesn't stay on. Calls from one caller alert or ring a member at most three times in two minutes, enough for a redial, unless the member takes one (`huddle/ring.rs`), so nobody can ring someone nonstop; calls in a DM the member muted don't count. Huddles are capped at 8 people, and a device keeps at most 16 audio links whatever the roster says. Huddle audio isn't end-to-end encrypted beyond the QUIC connection between the two devices (see Known gaps). See `huddle/`, `workspace/huddles.rs`, and the attack tests in `tests/huddles.rs`; for the audio layer, `crates/shy-media/src/access.rs` and its attack tests in `crates/shy-media/src/tests/calls.rs`.
- **Status:** a status (emoji, up to 100 characters, an end time, which alerts you want meanwhile) is an ordinary op, so only its author can set it. Longer ones, or ones with control characters, line breaks, or invisible characters that hide or reorder text (like right-to-left overrides), are skipped, so a status can't disguise the name beside it. Its alert level only quiets your own notifications, and never makes a muted channel louder; it isn't enforced on others.
- **Profile details:** a member's title, pronouns, bio, email, phone, website, working location, time zone and working hours are an ordinary op, so only their author sets them, and the newest by lamport clock wins. Every member sees every filled field, as do agents and people who join later; a removed member's details stay as they last were. Replacing or clearing a field hides the old value in the app, but every earlier version stays in the encrypted log, where any member (also one who joins later) could dig it out, as with deletes. Details sealed into a private channel or DM count for nothing, and a removed member's late changes are undone like their other late ops. Details from others are cleaned the same way on every device (`profile.rs`): free text (title 80 characters, pronouns 40, bio 300, location 80) loses control and invisible characters, like names, and is cut; an email (254), phone (32), website (200) or time zone (64) that is too long or malformed is cleared instead of cut, since a cut one could point somewhere else. An email or website with a character names may not hold (control, invisible or tag characters) is cleared too. Only http and https websites survive (no `javascript:`, `data:` or `file:`), and none with a user name before its host (`https://bank.example@evil.example` reads as one site and opens another) or a `\` there; an email can't carry anything that would add to its `mailto:` link, a phone holds only digits, spaces and `+ ( ) - .`, and working hours out of range are dropped. One bad field never voids the rest. Your own details are refused rather than changed.
- **Admin recovery:** the recovery kit is a secret (recovery key plus bucket credentials). Snapshots in the bucket are encrypted with a key derived from the recovery key and bound to the workspace id. They hold no content (messages, pages, files, pictures, profile details), only what makes the admin the admin. One too large for restore to read isn't uploaded; the storage settings report the last snapshot's size and the limit, and Settings › Recovery warns the admin from three quarters full, then says the kit can no longer restore and stops offering one; the membership change still goes out, and restore then refuses the older snapshot as stale rather than splitting the group. A snapshot is always uploaded before the commits it covers (adding or removing a member waits for a sync pass in progress, since a pass re-uploads commits it finds missing), and restore refuses a snapshot when the bucket holds any admin-signed commit from the snapshot's epoch onward (a rolled-back or stale snapshot). Deleting those slots doesn't help: members re-upload them. A restored device writes nothing until it has read its own log back from the bucket: the snapshot marks its store as catching up, every op write is refused while that mark stands, and the next sync that reads the own log back with none of it left waiting clears it, and only then writes what opening held back (the sealing key, for one). A change of our own that came back but can't apply yet (one from a newer version of the app) keeps the mark, and restore then asks for an update; only one we signed counts, so nobody can plant one to hold a restore up. A restore that fails is shut down and waited out before its files go, so a retry never runs beside it. So a restore never reuses a sequence number the bucket holds, which every member would prove a fork, also when the app quits mid-restore. Restore succeeds once that own log is read; an object nobody can read in another member's log doesn't block it (it's read, or given up, like on any other day), while one in the admin's own log does, and is never given up on while the device catches up (elsewhere an object that fails three times is given up). A failed restore removes only what it created. See `membership/recovery.rs`.
- **Changing the bucket key after a removal:** a removed member keeps the shared bucket key until it is deleted at the provider. Each removal marks the key in use as one a removed member had and asks the admin to change it (Settings › Storage): they make a new key at the provider, and the app checks it and sends it as storage settings, under the epoch key the removal replaced, so the removed member never learns it. A key a removed member had is refused if entered again, and the rotation can't end while one is in use. Members' heads name the key they use (a short hash of its access key id), so the admin sees who has moved; a hint only, as heads are unsigned (a removed member can still write them with the old key, so "moved" can be faked until that member's app rewrites its head). Deleting the old key before everyone has moved cuts off whoever hasn't (they can't read the bucket to learn the new key), so they need a new invite; the app says so and leaves the choice to the admin. The app then proves the old key dead: one read of a head with the current key, then the same with the old one; only a refusal (401 or 403) right after the current key worked counts, never a network or server error, which is retried every 10 minutes. The old secrets are kept, encrypted, in the admin's store and so in the recovery snapshot (which needs the recovery key), only until each is proved dead or the admin stops the rotation; the snapshot is redone then. They are never logged, and every key replaced during a rotation must be proved dead before it ends. The new key also changes the recovery kit, which holds it (`workspace/key_rotation.rs`, #135).
- **Storage settings:** only the admin can change the bucket region and keys. New settings are checked against the bucket first, travel as an admin-only op encrypted with the current epoch key (so removed members can't read them), and ops claiming to change settings from anyone else are skipped. Every member also skips settings that change the endpoint or bucket, or leave the region or a key empty, so a buggy or hostile admin op can't point everyone somewhere they can't open the workspace from. Newcomers get the settings with their version, so older changes replayed later can't put back revoked keys. The recovery kit holds the keys too, so after a change the app shows the admin a new kit; older kits stop working once the old key is deleted. Plain `http://` endpoints are refused unless the server is on the local network. See `workspace/storage.rs`.
- **Sealing keys:** each member announces an X25519 public key (in a signed op) that others use to hand them private channel keys with HPKE. It is separate from the identity and MLS keys, so no key does two jobs. Malformed ones are skipped. The secret stays in the encrypted database and is part of the admin's recovery snapshot. See `private/`.
- **Private channels and DMs:** their content is sealed a second time, under a channel key, inside an ordinary signed op. Other members, the admin and the bucket see that someone wrote something private, when, and how big, but not which channel or what it says; even the key hint differs for every op, so they can't tell which ops belong together. The number of wraps in a key grant does hint at how many people a channel has. Rules, all checked the same way on every device in any arrival order (see `private/rules.rs`):
  - *Keys* reach members wrapped with HPKE to their sealing key, bound to the workspace, the granter and the recipient. Wraps carry no recipient list; each device tries them all (at most 512 per grant); keys that contradict what the owner announced are dropped. Content and hints derive from the key together with its channel and generation, and a sealed payload opens only in the op slot (workspace, author, sequence) it was written for, so neither a key handed out under another label nor a payload copied into another op opens anything.
  - *A key counts only if the channel's owner vouched for it:* the creation and every new key come with a commitment (a hash of the key) in a sealed op all members read. A key nobody vouched for is never used to send and nothing sealed with it applies. A channel's id names its creator and commits to its first key, name and members, so only one creation can count.
  - *The owner's log:* adds, removals, new keys, hand-overs and owner deletes are numbered per channel and apply only as exactly the next number, written by whoever owns the channel at that number (its creator until a hand-over). So every device judges each of them against the same state. The admin can't see or manage private channels; their lever is removing someone from the workspace (which, through succession, can also change who owns one).
  - *Who belongs when:* an add says which of the newcomer's ops it starts after and which key generation; a removal ends their latest time whatever the owner had seen of their log; a leave ends it at the leave. An op counts only if its author belonged at that point, with a key from then. One sealed with an older key than the newest, by someone who doesn't belong, never counts; everything else that doesn't count yet waits. Content applied before a removal or leave arrived is undone: the device rebuilds its views, settling the owner logs, then leaves, then content, each in its authors' order. If an owner writes two ops for one number, the earlier in their log wins.
  - *Succession:* if the admin removes a channel's owner from the workspace, the member they added earliest who is still around takes over with a claim at the next number (members added together are ordered by key; leaves don't count, as devices learn of them at different times). A claim counts only once the device knows the owner's removal and has their whole log up to it, holds every key announced so far, and knows that each member ranked earlier was removed too; until then it waits. It must be written after the owner left the workspace, so nobody can plant one in advance. The successor's device writes it on its own, then removes the old owner (a new key); a successor who had left the channel passes it to the next member. Someone ranked earlier who is still in the workspace but can't claim (never opens the app, runs an older version, or left the channel and missed a key) holds this up until they are removed. A member the owner removed from the channel is never in line. An admin who is in a channel can make themselves its owner by removing its owner and everyone ranked above them from the workspace. See `private/succession.rs`.
  - *Removal* makes a new key for everyone else; the owner's device also removes on its own whoever left or was removed from the workspace. A removed member keeps what they already read. Someone added later can read the history.
  - *Who has joined:* the owner can list someone without giving them the key, so the member list marks a member "Invited" until an op of theirs, sealed with a key from their latest add on, has counted in the channel (old ops never prove a later add). Once a member's device holds that key and they have read a message sealed with it (opened the channel, or marked it read), it writes one small `Joined` op, once per membership; an add or a re-add alone never makes a device write. This tells the channel's members, once, that they read it. Others can't open it, but they can see that someone wrote a small sealed op, and so roughly how many private channels a member joined and when they first read each. Anyone in a channel with no messages yet stays "Invited". A member whose device is still listed but missed the newest key the owner announced (left out of a rotation) is told so in the channel. Nothing here decides what counts. See `private/actions.rs` (`confirm_joined`).
  - *Ordinary ops can't reach private ids:* private ids contain a `:`, which public ids never do, and an ordinary op naming one is skipped (even an admin delete). Content sealed into a channel may only name that channel and its messages; only the author edits or deletes a message, and the owner deletes others' through their log. For a message id used twice, the one earliest in its author's log wins, in any opening order.
  - *DMs* have a fixed member list; the id is a hash of it, and keys are accepted only from and for those members. Each member writes only with a key they made and granted to every member themselves, so nobody can hand someone a key the others lack and have them write into it unread (#72). Members read under any of the DM's keys. Notes to yourself are a DM whose only member is you, so only your own grant counts and only you can write there.
- **Shared files:** a file's bytes are encrypted with a fresh random key, in 4 MiB pieces sealed with XChaCha20-Poly1305 in the STREAM construction, so pieces can't be reordered, dropped or cut short; equal files look unrelated (no deduplication). The key travels only inside the signed `File` op, so a file is exactly as private as the place it was shared in: sealed with the channel key in a private channel or DM, readable by every member in a public channel. That op also holds a BLAKE3 hash of every sealed piece. Everyone who can read a file holds its key and every member holds the bucket keys, so without the signed hashes a member could swap a piece under its author's name; a piece that doesn't match is refused before decrypting and never cached. A file op must use an id its author owns, attach only to the author's own message, name a well-formed blob of at most 4 GiB whose piece count matches its size (far above the 150 MB this version sends, so a later one can raise it, but bounded, so a forged size can't make a device reserve huge amounts), and, sealed into a private channel, stay inside that channel; others are skipped. A file shows with a message only if both name the same channel. Files are opened whole in memory only up to 64 MB; larger ones are streamed to disk by Save as. Names lose control and invisible characters and path separators, and can't start with a dot; a media type that isn't a plain `type/subtype` becomes `application/octet-stream`, and the app decides how to show a file from its first bytes, never from its name or type. The bucket sees each blob's author, its piece count and size, and when it was written, but not which file, channel or reader it belongs to. Pieces are cached on the device still encrypted, by author and blob id (ids are public, so someone could reuse one under their own prefix; it never stands in for the original), and a cached piece that fails its hash is dropped and fetched again; their keys sit in the encrypted database. See `files/`, `transport/blobs.rs`, `workspace/files.rs`.
- **Files in pages:** a file shared into a page (`Workspace::share_page_file`) has the page as its place and no message, and everyone who can read the page can read it. A page reads only its own files: `page_file_bytes` and `save_page_file` refuse any other, so a page's text can't pull in a file shared in a channel, a DM or another page by naming its id (the page view must use these, not the general `file_bytes`). Deleting a page, which its creator or the admin may do, deletes every file in it with their pieces, whoever shared them, as deleting a channel does; a file that arrives after its page was deleted is dropped.
- **Renaming a file:** only its sharer may (the id names its owner, as for message edits); anyone else's rename is skipped, and in a private channel or DM it also has to stay inside that channel. The newest rename by lamport clock wins, kept apart from the file so it applies in any arrival order, and a deleted file's rename brings nothing back. A new name from someone else is cleaned like any file name; your own is refused rather than changed if cleaning would alter it. Earlier names stay in the encrypted log, as edits do. Renaming changes only the label: the bytes, their key and their hashes stay as signed.
- **Deleting a file** (or its message, channel or page) is stronger than deleting a message: besides leaving every app, its pieces leave the bucket, removed by the device that deleted it, on its next sync pass (only that one, since a delete can later turn out not to count, for example when its author was removed at the same moment; a rebuild drops removals still waiting, but pieces already removed are gone, and the file then shows but can't be opened), and every device drops its cached copy. A file that arrives after its delete (a rebuild or restore reads the bucket in a new order) still leaves the bucket through whoever deleted it. Someone who already opened or saved it keeps that copy, and a bucket that keeps old versions keeps the pieces until its own rules expire them.
- **Profile pictures** are a `ProfilePicture` op pointing to a blob of at most 512 KB, checked as PNG, JPEG or WebP when shared; others' larger ones are skipped. Every member sees every picture. The app re-encodes a picture before sharing it, which drops the photo's location and camera data. The picture a new one replaces leaves the bucket, never the one still shown; two with the same clock (only a forged op makes that) settle on the higher picture id, the same in any order.
- **Workspace icon and look:** only the admin sets them (`WorkspaceIcon`, `WorkspaceLook`); anyone else's op is skipped everywhere, and the app refuses to send one. The icon is checked like a profile picture (at most 512 KB, PNG, JPEG or WebP, re-encoded by the app) and lives in the admin's blobs. Theme and accent names must be 1 to 24 lowercase letters, or the op is skipped; the core never interprets them, and an app shows a name it doesn't know as its default. The latest of each wins by the admin's clock, a tie going to the larger value, the same in any order. Anyone can choose their own look on their device; the admin's is only the default.
- **Files in the desktop app:** the window never handles paths. Files the person picks (a native dialog opened by the Rust side), drops on the window (taken from the window's own drop event) or pastes become opaque tokens in `src-tauri/src/files.rs`, and sending names only tokens, so a bug in the UI can't make it upload some other local file. Save as asks where with a native dialog from the Rust side too, and writes nothing until every piece has arrived and checked out. Images show inline only when their first bytes say PNG, JPEG, GIF or WebP, whatever their name or media type, and only from memory as `blob:` URLs (the one addition to the window's `img-src`); anything else, SVG included, is a card with Save. Images are checked for the size their header claims before decoding (JPEG fill bytes and a GIF's first frame included), so a small file can't demand gigabytes when shown, and only images up to 5 MB load without being asked. Text files open as plain text, never as HTML, and markdown goes through the same renderer as chat. PDFs (up to 25 MB, and only when their first kilobyte holds the PDF marker) are drawn as pictures by pdf.js in its own worker, loaded only when one is opened: its scripting viewer isn't included, forms (XFA) and WebAssembly decoders are off, no image or page may exceed 25 megapixels and all drawn pages together 80, at most 30 pages are drawn, drawing gives up after 30 seconds, and links in the PDF are never drawn as anything clickable. What pdf.js uses while parsing isn't bounded: a PDF that inflates into gigabytes (a decompression bomb) could still exhaust memory and crash the window, though nothing in it can run. The worker's script is served without the page's content policy (Tauri adds it to HTML only); that would matter only after pdf.js itself was compromised, and the worker can't call the app's commands. pdf.js parsed a crafted font into running script in 2024 (CVE-2024-4367); version 6 has no such code path left, and it's pinned and updated like any security dependency. Pictures are re-encoded by the app before sharing (`lib/picture.ts`).
- **Desktop notifications show message text** to the operating system's notification center, outside the app's encrypted storage. Settings → Notifications can hide the text, leaving only who wrote and where. The sender's picture (their avatar: initials on a colour) is saved unencrypted in the app's cache folder, one file per member id, for the notification service to read; the native side accepts only a small PNG named for a member id (`src-tauri/src/alerts.rs`).
- **Personal state isn't shared:** read positions, alert levels, drafts and saved-for-later items never leave the device (drafts sit in the encrypted database, not browser storage) and aren't in the admin's recovery snapshot, so other members (and the bucket) can't see what you've read.
- **Encryption at rest:** both local databases use SQLCipher with keys derived from a device key kept in the OS keychain (or a key file the user places elsewhere). The identity key and bucket credentials are inside the encrypted database; `workspace.json` holds only public settings (the workspace's name, id and admin), and the id and admin are checked against a copy in the encrypted database, so editing the file can't name a new admin, and a store without that copy doesn't open. See `keys.rs`, `storage/mod.rs`, `config.rs`.
- **Chat rendering:** messages become React elements through react-markdown, never HTML: raw HTML and images are dropped, and only http(s), mailto and `shy://` page, message and mention links survive (`lib/markdown.tsx`); any other link shows as its plain text. Page titles come from other members and never enter the markdown source: a bare page link becomes a link with an empty label, and the page chip draws the title as text, so a title like `<https://…>`, one ending in `\` or one with a backtick can't become a link out or break the message. The page editor links pages the same way: picking a page inserts `[](shy://page/<id>)`, and its chip draws the current title. Page, message and mention chips never show the author's label: a page chip draws the page's current title, a mention its member's current name (with a safety code when two share a name; "member 1a2b3c" for someone unknown), @channel and @here their own words, and a message chip "a message". So `[@Ada](shy://member/<eve>)` can't show "@Ada" while it notifies Eve, nor `[Payroll](shy://page/…)` a trusted name for another page; and as all of it is drawn as plain text, markup can't put a link out inside a chip. One-line previews (Inbox, quotes, drafts, Later, search, thread summaries; `lib/plainPreview.ts`) read the whole message with a markdown parser (`mdast-util-from-markdown`, the one under the chat's renderer), so every spelling of a link (an `<address>`, brackets or emphasis inside the label, a title, a reference to a `[label]: address` definition) is named the same way, keeping a label only when it already says the true name; the line is shortened only after that, so no link is cut. A message the chat shows as plain text, being too costly to format, previews as that plain text, address and all. Thread summaries, search snippets and desktop notifications come from the core as plain text with every app link already named by its target (`markdown::preview_text`), read with the markdown parser, so a reference link resolves wherever its definition is and a cut can't leave a label behind. Images, which chat doesn't show, add nothing to previews or the search index, not even their alt text, and previews drop control characters, so a message can't fake a snippet's match marks or put them in a system notification. A page's snippet reads only what the index holds of it. A message shows at most three page cards and three message cards (each loads its own data), and a shown message card reloads only when its own channel changes, so one message full of links can't keep every reader's app busy; the other links stay in the text. External links show their full address on hover and open in the system browser. In chat and in pages (Ctrl+click), a link asks before opening when it could mislead about where it goes (`isMisleadingLink` in `lib/contact.ts`): its text shows a different address than it opens, even with invisible characters (zero-width spaces, soft hyphens, direction marks) slipped into the text to hide the address, or the address names a user before its host (`https://bank.example@evil.example`), which opens the part after the `@`. Links in chat, in pages and on profiles open with the system's own apps (browser, mail, phone), always through `lib/contact.ts`: the scheme is lowercased and a `mailto:` link loses its query, since mail apps may honour parameters like `attach=` that hand them a local file. The window itself may hand the system only `http`, `https`, `mailto` and `tel` addresses, and no `mailto:` with a `?` (`src-tauri/capabilities/default.json`), so a slip in the app can't open anything else. Text too costly to format (deep nesting, huge tables, long runs of emphasis marks, very many lines; `lib/markdownBudget.ts`, which deliberately doesn't imitate the parser's rules and counts on the high side) shows as plain text, as does anything the parser builds with too many parts or too big a table (a remark plugin, the second net), and a message that fails to draw falls back to plain text, so one message can't freeze or blank the app; a top-level fallback offers a way back to the first channel.
- **The window stays the app:** the main window is built in code (`src-tauri/src/window.rs`) and refuses every navigation away from the app's own pages, every new-window request and every download, whatever starts it (the web view's own right-click menu, a middle-click, a script). Links open in the system browser only through the app's own handling.
- **App updates:** installed apps update from the latest published GitHub release (`src-tauri/src/updates.rs`, Tauri's updater). Every update package is signed with the updater's minisign key; the public key is built into the app, and the updater refuses a package whose signature doesn't match before installing it. The private key and its password exist only on the admin's machine and as secrets of the `release` environment, which only builds of v* tags can use. The signature also carries the version (`requireSignedVersion`): `latest.json` isn't signed, so without it anyone able to edit a release's files could offer an older signed build as a new version and roll devices back. An update installs only when the person restarts for it, never during a huddle, and after unsent changes are uploaded. The page can only ask whether an update is ready and to restart into it; it can't choose what gets installed, since the updater's own commands aren't exposed to it. Whoever holds the key, or can run a v* tag build, can ship code to every device. During a tag's app build the key and its password sit in the build's environment, where any build script of a dependency could read them; and anyone who can push a v* tag can run that build with a workflow they changed. Keep who may push tags tight (a tag ruleset, required reviewers on the `release` environment).

## Known gaps

- A device that dies right after sending live loses those ops for everyone if no member holding them stays online for the next few minutes (to relay them), and a restored admin then reuses their seqs: the members who got them see both versions proved a fork and drop them. Restoring within those first minutes has the same effect.
- Bucket credentials are shared by all members, so any member can cause denial of service, or delete the workspace's data unless the bucket keeps it. Segments are written create-only (If-None-Match), so with a bucket policy that refuses overwrites under `ops/`, no segment can be replaced; nobody can take a segment's name first, since it holds a random nonce picked at upload (#139). Commits are plain puts on purpose: a commit slot's name is predictable, so create-only would let someone take it first. What protects them is that they're admin-signed (readers refuse anything else) and that every member puts a missing or altered commit back at its next 10-minute duties, so a deleted or overwritten commit is out of the bucket for at most about 10 minutes while someone is online; versioning or a lock (S3 Object Lock keeps older versions when a plain put adds a new one) keeps the real commit recoverable even if nobody is. A retention lock on the write-once `ops/` (Cloudflare R2 bucket locks, S3 Object Lock) also stops deletes there. Don't lock `mls/` with a lock that refuses overwrites (an R2 bucket lock does): junk put at the next commit slot would then block every later membership change, removing its author included; versioning (S3, Backblaze B2, MinIO) undoes accidents, but the shared keys can delete old versions too unless the provider's key rules forbid it. The admin's recovery snapshot (`recovery/snapshot`) is overwritten, so it can't sit under a lock; keep the recovery kit and a working admin device. The app proves which protection holds, daily, by writing small probes (`health/versioning-probe`, `ops/lock-probe-<member>`), and Settings warns until it's locked (`workspace/protection.rs`, #83). It can't tell S3 Object Lock from plain versioning, so it reports that as versioned.
- Shared files aren't under the lock that protects `ops/` (they must stay deletable), so anyone with the bucket keys can delete or overwrite their pieces; a changed piece is refused, but the file is then lost unless the bucket keeps versions. A removed member keeps the bucket keys until the admin changes them (the app asks after every removal), and until then can still fetch the pieces of files shared before their removal, whose keys they already had. See #122.
- **Huddle ghosts on public channels:** gossip doesn't say who first sent a message, so a member can replay another member's recent "joined" beacon (within the 2-minute clock skew) to a device that never heard that session, for example one that just restarted. The same works on a device that lost track of the session for 90 s (a dropped network) and missed its leave. The person then shows in the huddle for up to 90 s, but no audio flows, since nobody publishes at that session's path any more. Private huddles aren't affected: their beacons are bound to the sending device.
- **Huddle audio over relays:** audio is encrypted between the two devices by QUIC, so a relay can't hear it, but it isn't sealed with the channel's key as messages are. Adding SFrame-style encryption with the channel key, for private channels first, is planned (#15).
- Single admin. A recovery kit restores a lost admin device, but there is still only one admin at a time; restoring while the old device is alive would cause conflicting membership changes (#5).

Issues labeled `security` track these: <https://github.com/shynewt/shyspace/issues?q=label%3Asecurity>

- A restored admin can reuse sequence numbers of ops that reached peers only live before the old device died (#26).
- Restore trusts the bucket to hold the admin's whole log. Someone with the bucket keys who deletes the admin's newest uploads before a restore makes it reuse those sequence numbers, which members holding the deleted ops then prove a fork; deleting one from the middle, or planting an object under the admin's name that can't be downloaded, instead stops the restore until the bucket is put right.
- In a group DM, a participant can show their own messages to only some members, by writing them with a key only those members got. Members on versions before #72 can still be led to write with such a key (#111).
- A private channel's owner can leave a member who already joined out of a new key; only that member is told, and the others still see them as in. A hostile owner can also withhold older keys from someone they add.
- A private channel key that leaks stays useful until the next removal or rotation. Bots read only the private channels someone adds them to; public channels are readable by every member, bots included.
- A member can still send page updates whose pieces name neighbours that contradict each other or don't exist yet. yrs then places text differently depending on how it holds the page in memory (even saving and reloading a page can move such text), so pages can read differently on different devices, after a rebuild, or depending on whether the updates arrived one by one or in a downloaded batch, which is merged in memory (#186); in debug builds it can panic while merging.
- A page editor's client id is 53 bits of a hash of the author, page and a nonce the author picks. A member can spend about 2^53 hashes once per page to build a lookup table of their own nonces; after that, matching any new editor session's id on that page takes seconds. Devices that get the two edits in different orders then keep different text, and the other person's edits are refused. Renewing an editor's id daily doesn't stop it (#210).
- A page update may delete any client's text, including clocks that client hasn't written yet: yrs keeps such deletions and applies them when the text arrives. A member who has seen one update from an editor session can send one op that deletes the rest of that session's typing as it lands. Devices still agree. Refusing it would make the verdict depend on arrival order (#212).
- A sealed op of a kind a newer version added waits silently in its channel until this app is updated.
- A hostile member can make others' devices do extra work with junk grants and sealed ops that never apply (the denial-of-service gap above).
