# Decisions

Why things are the way they are. Add an entry when you make a choice that someone might later question. Newest first.

## Huddles: no push-to-talk, no "you're muted" warning, no huddle status on profiles (2026-11)
Muting closes the microphone, so the system's mic light goes dark; nothing can listen for "you're talking while muted", and push-to-talk would cut off the first words while the mic reopens. App-wide push-to-talk keys are also unreliable on Wayland. Instead, Mute says its state in words and is tinted while muted, which research found is what stops people talking on mute. Profiles and member lists don't say who is in a huddle: it would show who is talking with whom, and a private channel's huddle must stay hidden from non-members. Channels never ring; a DM rings once, since nagging about channel huddles is what people most often turn off elsewhere.

## Frequent things don't animate; scrims don't blur (2026-11)
Animations felt slow in daily use, so how often something happens decides how much it moves (see Motion in `design-system.md`). The command palette opens and closes with no animation, since it's used many times a day. Whatever a key changes changes at once: a highlight moved by the arrows jumps instead of sliding, because keyboard users move fast and a slide makes them wait to see where they are. Scrims behind dialogs and the drawer only dim: a backdrop blur is redrawn on every frame, which WebKitGTK does slowly, and it made opening a dialog stutter.

## Mobile apps will be native, on the shared Rust core (2026-11)
iOS and Android get native interfaces (SwiftUI and Jetpack Compose) that call `shy-core` through generated bindings (UniFFI), not the desktop's React app in a Tauri mobile web view. A chat app is judged on fast scrolling lists, the keyboard, back-swipe and screen readers, which web views on phones do worst; Element X and Bitwarden made the same move onto a shared Rust core. What's shared is the core and the design rules (tokens, type scale, motion, behaviour); the screens are rewritten, and the page editor may stay an embedded web view. So the desktop layout is responsive for desktop windows only (full screen and split screen), and logic that every app needs belongs in the core, not in TypeScript. Mobile work is #19.

## Profile details: a new op, every field public, cut or cleared (2026-11)
Title, pronouns, bio, contact, time zone and working hours travel in their own op, `ProfileDetails`, not as new fields on `Profile`: ops are postcard, which reads fields by position, so a longer `Profile` would stop every old `Profile` op from decoding. Versions before it park a member's ops from their first details onward until they update, the same cost as every new kind of op. Every filled field is visible to the whole workspace; there are no per-field audiences, which would need per-field keys. Free text from others is cut to its limit, like names; an email, phone, website or time zone that's too long or malformed is cleared, because a cut address can point somewhere else. Pictures wait for files (#13).

## Views switch without an exit animation (2026-11)
A view fades in (in 100 ms: switching is frequent); the one it replaces goes at once. With an exit animation (Motion's `AnimatePresence mode="wait"`), switching again while the new view was fading in could leave Motion waiting forever on the exit, with nothing shown. Slow frames made that common, and WebKit's tests caught it. A UI test switches views quickly on simulated slow frames.

## UI tests run in WebKit too, in a container locally (2026-11)
The app runs in WebKitGTK, and Chromium-only tests let WebKit bugs through. Playwright's WebKit build needs Ubuntu's libraries, so locally it runs in the official Playwright image with Podman (`pnpm test:ui:webkit`); CI runs both browsers directly on Ubuntu. The WebKit tests claim a WebKitGTK user agent, because Playwright's WebKit poses as Safari on a Mac and the app picks Mac shortcuts from that.

## Emoji data ships with the app (2026-11)
The emoji picker is frimousse, on Emojibase data. By default it downloads that data from a CDN, which would tell a third party when someone opens a picker in a private app. And the app's content policy lets the page connect only to the core, so it can't fetch the data even from itself. So `ui/emojiData.ts` imports `emojibase-data`'s English files as a lazily loaded module and hands them to the picker; the picker itself loads on first open too, so neither weighs on startup. That function is the one place that builds the categories, so a later "Custom" category goes there. A UI test fails if the picker makes any request outside the app, or doesn't work under the app's connect rules. Because the data is ours, frimousse doesn't check which emoji the system font can draw; we offer Emoji 15.1 and older. Updating emoji means updating the package.

## No link previews (2026-11)
The app never fetches a link to show a preview. Fetching would tell the linked site who is reading what, outside the encryption, and previews are a known way to leak data out of AI agents' context (Slack's MCP server did). Links stay plain.

## Replies are threads, built on reply_to (2026-11)
One reply model: a reply lives in a side-panel thread instead of the channel, like Slack, with Zulip's attention tools (follow and unfollow, following threads you join). Threads are optional, never forced like Zulip topics. Thread replies don't add to a channel's unread count, but a mention in one still does, until you've read it in the channel or the thread. No new op was needed; a title and a "resolved" mark would need one (#58).

## Mentions are markdown links; @here means @channel for now (2026-11)
A mention is a link in the message text, not a separate op: nothing new to sync or secure, agents read and write them as plain markdown, and copying a message keeps them. Each device decides what mentions it, exactly, even though everything is encrypted. Until presence exists (#42), @here reaches everyone like @channel.

## Editing and deleting: owner or admin, hide and purge (2026-11)
Only authors edit their messages. Owners delete their own channels, messages and pages; the admin can delete anything, to moderate. Anyone may rename a channel (like page titles). Deletes are permanent markers, so they converge in any order; a deleted page's sub-pages move to the top level instead of disappearing with someone else's delete. Delete purges the views and search but can't erase the encrypted log other devices already hold; `security.md` says so.

## Admin recovery: kit plus snapshots in the bucket (2026-11)
A one-off export goes stale after the next membership change, and restoring a stale MLS state can reuse message keys. So the admin's app uploads a fresh encrypted snapshot after every membership change, and the kit only holds the key to it. Content (messages, pages, files, pictures) is left out of the snapshot; a restored device re-downloads it. Real multi-admin stays open (#5).

## Local encryption: SQLCipher plus a device key in the OS keychain (2026-11)
SQLCipher encrypts the whole database, including indexes and the search index, with little code on our side. The key lives in the OS keychain so the data directory alone is useless. Servers without a keychain use an explicit key file (`--key-file`); there is no silent fallback. SQLCipher links the system OpenSSL for development; release builds turn on the `vendored-openssl` feature, which builds OpenSSL into the app, because macOS and Windows have no system copy to rely on (it needs Perl on the build machine, which GitHub's have).

## Invites: single-use, approved, credential-free (2026-11)
A reusable code containing bucket credentials meant anyone who saw it could join and could vandalize the bucket. Invites now carry only presigned links (one upload, one download) that expire after 7 days, and the admin approves each request. Credentials travel inside the MLS-encrypted answer.

## Pages are markdown in one Yjs text (2026-11)
Agents edit pages from Rust (yrs), people from the editor (Yjs). A block editor like BlockNote stores a complex XML tree that would be hard and fragile to edit from Rust. Plain markdown keeps one simple shape for both, makes search and export trivial, and still gives live collaboration.

## Ids carry their author's key prefix (2026-11)
With "earliest creation wins", any member could take over another's message by reusing its id with an older clock. Tying ids to the author removes the conflict entirely.

## Only the admin changes membership (2026-11)
MLS needs commits applied in one agreed order. Without a server, concurrent commits from different members would split the group. One committer avoids that. Several admins is a future problem (see issues).

## MLS for keys, our own envelope for content (2026-11)
MLS messages can only be decrypted once and in order, which doesn't fit a sync log that new members must read from the start. So MLS only agrees on one secret per epoch; content uses keys exported from it. Newcomers get older keys in an admin-sent keyring.

## Two transports: iroh gossip and an S3 bucket (2026-11)
Gossip gives instant delivery when people are online, with NAT traversal. The bucket is a "dumb" mailbox anyone can rent, so nobody has to run a server. Since all ops merge in any order, both can carry the same envelopes.

## Tauri, not egui (2026-11)
The product is mostly rich text. The web ecosystem has mature editors (CodeMirror, Excalidraw later); egui would mean writing those from scratch. Cost: more memory, and WebKitGTK quirks on Linux.

## Rust core shared by every client (2026-11)
One engine for desktop, CLI, agents and later mobile. Crypto and sync are written once.

## Voice huddles before screen sharing; native mobile apps later (2026-11)
Product scope set by the owner. Mobile is wanted mainly for notifications, which will need a small push relay that sees no content.

## Presence over gossip only; status as an op (2026-11)
Presence changes every few minutes and is worthless a minute later, so it travels only as signed heartbeats over gossip and is never written to the bucket, which would keep a log of when everyone was around. A member who can't reach peers directly shows as "not reachable" rather than "offline", because the app can't tell the two apart. A status is meant to last, so it is an op that syncs like any other and reaches people who were away. Cost: a version older than this one can't read a status op, and because each member's ops apply in order, it holds back everything that member writes afterwards until it updates (it tells the user to update). Statuses set to "As usual" or "None" read fine there; "Mentions only" is the one older versions can't read. Older versions also log a warning for each heartbeat they can't read.

## Over-long text from others is cut, not refused (2026-11)
Messages, edits and page titles from other members are cut to the limit (40,000 and 200 characters) instead of skipped. Devices from before the limit accepted such ops, so refusing them now would make old and new devices disagree about whether a message exists, and would hold up the author's later ops. Cutting by characters is the same on every device. Cost: a cut can split an emoji or a link at the very end, which only looks odd, and old devices still show the whole text until they update.

## Oversized ops are refused, not cut (2026-11)
An op over its size limit (4 MB for a page update, 256 KB otherwise) is recorded as handled without its content, unlike over-long text, which is cut. A Yjs update or a key grant can't be cut and still mean anything, and keeping the bytes is the very cost the limit removes. Older versions still accept such ops: they show a page update over 4 MB, and an oversized message cut to its first 40,000 characters, where new versions show nothing. Honest ops never get that large apart from rare giant pastes made on an old version, and new versions never send one, so in practice only ops built on purpose look different. One limit per kind rather than per field keeps the rule to a single check on the sealed size.

## Forked ops are dropped, not resolved (2026-11)
When an author signs two different versions of one op, neither counts anywhere, and the proof travels as a bucket object rather than an op. Picking a winner (say the lower hash) would let the author rewrite an old message on every device by signing a new version, and each new version would force another rebuild. Freezing the author's log at the fork would end an honest restored admin's log for good (#26). An op carrying the proof would share its reporter's fate (a freeze could cut it on some devices) and older versions would stop applying every reporter's later ops. Hash-chaining each author's log would stop forks at the source but changes every op; we didn't, for now.

## Joining a private channel: one note, after reading (2026-11)
A member counts as joined once an op of theirs, sealed with a key from their latest add on, counts in the channel; a device that has the key and was opened writes one `Joined` op for that (#110). It isn't written as soon as the key arrives: then anyone listing people in a channel, or every rotation, would make many devices write at once, which shows outsiders who is in each channel and can be abused. It isn't per key generation either: everyone would turn "Invited" after each rotation, and each new note would be a read receipt. The cost is a one-time signal to the channel's members that you opened it.

## Private channels: key grants with commitments, one owner (2026-11)
A private channel's content is sealed under its own key inside an ordinary op, so sync and gap-free logs keep working for everyone. Keys reach members wrapped with HPKE to a per-member sealing key; a removal makes a new key for the rest (the scheme of Signal's sender keys and Matrix's Megolm). We didn't use one MLS group per channel: MLS needs one agreed order of membership changes, which only a server or a single always-online committer gives. Instead each channel has one owner who changes membership and vouches for every key with a commitment, so everything merges in any order and nobody can slip in a fake key. People added later read the history, like Slack. Owners can hand over, and when the admin removes an owner from the workspace, the member they added earliest takes over: computed from facts every device ends up knowing (the removal, the owner's log up to it, the order of adds), written as a claim at the next number so it lands in the owner log like any other change. We didn't let the admin pick (they can't see private channels) or let members race to claim (devices would disagree on who was first). DMs are fixed member lists with no owner, and each member writes only with a key they made and granted to every member themselves (#72). Otherwise one member could hand Bob a key Carol never got, and Bob would write to them both unread. We didn't make members confirm each key before it counts: one member offline, on an older version or removed would stall the DM, and it still wouldn't stop a member showing their own messages to only some people. Reading stays open to any of the DM's keys, so older versions still read and are read. Cost: no healing after a device compromise until the next removal or rotation, and versions older than this one stop applying a member's ops once that member announces a sealing key (every member does on first start), until they update.


## Accent colour: six presets per device, not a free picker (2026-11)
Each person picks Violet, Blue, Indigo, Teal, Pink or Graphite for their own app. Hand-tuned presets can each be checked for WCAG AA in light and dark; a free picker would let people choose colours that make text unreadable. Red, orange and green are left out because they already mean danger, warning and success. A workspace brand colour set by the admin would need core changes and is not planned for now.

## Responsive desktop layout: container queries, a drawer, no icon rail (2026-11)
The layout follows the region's own width (CSS container queries) rather than the window's, so a docked thread narrowing the channel and a narrow window behave alike; JS reads the same width tokens only where behaviour changes (docked or sliding over). Below 760 px the sidebar is a modal drawer, and it can be hidden at any width, fully, as in Notion and Linear. We didn't add an icon rail: a channel list as icons is a column of "#". The thread slides over the channel without a scrim when the channel would keep under 560 px, so the channel stays readable at its edge and keeps working. Header labels fold into icons with tooltips, then into one Info popover, so the title is always the part that's cut last.

## Files belong to where they were shared; no folders or per-file sharing (2026-11)
A file's key travels in the op that shares it, in a channel or DM, so whoever can read that place can open it, and a private place seals it with the channel key it already has. "Share with these three people" means posting it in a group DM with them, and a restricted folder is a private channel. Folders with their own member lists would need a second membership log, key rotation and succession; and per-file exceptions are what users report going wrong in SharePoint and Google Drive. The drive shows where each file was shared instead. Folders may come later as labels inside a channel, never as a permission boundary (#127).

## File pieces: separate bucket objects, fetched on demand (2026-11)
A file is encrypted with its own key in 4 MiB pieces (STREAM over XChaCha20-Poly1305, `aead-stream`), and each piece is its own object under `files/<author>/<blob>/`. S3 multipart was rejected: a 150 MB object breaks the 32 MB bound readers keep, parts must be at least 5 MiB, and abandoned uploads cost money silently. Separate objects give retries and resuming with plain PUT and GET. The signed op holds a hash of every piece, since every member holds the bucket keys and every reader holds the file key. Files aren't copied to every device like ops; the bucket is their durable copy, and devices cache the pieces they opened.

## PDF previews with pdf.js, drawn as pictures (2026-11)
WebKitGTK can't show PDFs and macOS's engine can, so a native path would leave Linux without previews. PDFium (Chrome's renderer) is native C++ parsing hostile files inside the app's process with no sandbox; MuPDF and Poppler are AGPL and GPL; pure-Rust readers aren't mature enough yet. pdf.js runs as JavaScript inside the engine's sandbox, in a worker, on both systems, and only loads when someone opens a PDF (about 1.7 MB). We draw pages onto canvases with forms and WebAssembly off and never draw links, so a PDF can only be looked at; for anything more, Save opens it in the system's viewer.


## One lock for the workspace's state (2026-11)
The store (one SQLite connection) and the MLS group sit together behind a single `Mutex<State>`. An op's apply has to read and write both consistently, and one synchronous lock, never held across an `.await`, makes that simple and deadlock-free. The cost is that slow work under it stalls everything else: before #175/#176 a big channel's thread walk froze the app, and a downloaded segment held it for seconds until #179 saved segments in batches of 500. So work under the lock is kept short and bounded (indexed queries, batches), and network and file work happens outside it. If that stops being enough, the next step is a second, read-only SQLite connection for the views, so reading never waits for applying; the store and MLS state would still change together under the one lock.

## A patched copy of yrs, until upstream has the fix (2026-11)
yrs split and joined text pieces at a cost that grew with the square of their number, so one valid page update could freeze every device or exhaust its memory (#185). We couldn't work around it on our side: capping pieces per update refuses honest edits, splitting updates sends the pieces through yrs's slow pending queue, and joining pieces ourselves would place text differently from the editor. So `vendor/yrs` is yrs 0.28.1 with a small fix, used through `[patch.crates-io]` with the version pinned; `vendor/README.md` says what changed and how to drop the copy once a release has the fix. A git fork would hide the change outside the repo; keeping the copy here keeps it reviewed with the rest.

## Page editor ids bound to authors (2026-11)
A member could write page updates under another editor's Yjs client id, so devices disagreed and the victim's edits were refused (#187). Each update now carries a nonce, and its client id is a hash of the author, page and nonce, which every device can check from the op alone. We didn't use random ids, or let the first member to use an id own it: both depend on arrival order, which was the bug. The id has 53 bits because Yjs keeps client ids as JavaScript-safe integers, which leaves room for a precomputed attack (#210).

## Stored data is kept from v0.1.0 (2026-11)
From v0.1.0 on, stored data is kept: schema changes are additive migrations (`storage/schema.rs`), and a change to how views are built rebuilds them from the log rather than asking people to recreate their workspace. There is no support for old app versions: the updater moves everyone together, so a store from a newer app is refused with "update shyspace". Before v0.1.0 the schema was changed in place, which kept upgrade code from piling up while the format changed weekly.

## Search indexes visible words, with a markdown parser (2026-11)
Search used to index the raw markdown, so a query like "shy" or "member" matched link and mention addresses nobody sees (#76). The core now indexes only what a reader sees, using `pulldown-cmark` set to the flavour the desktop renders. A few regular expressions would have been smaller but get nesting, code and escapes wrong. Bare page links show as chips titled by the page, which can be renamed, so they are left out rather than indexed under a title that goes stale.

## Authors pack their own logs (2026-11)
A newcomer used to fetch one object per upload: about 10,000 after 30k messages, hours at company scale (#23). Each author now also uploads their log in aligned ranges of 16, 256 and 4096 ops, as ordinary segments, and readers fetch the covering chain first: about 25 objects per author plus one per 4,096 ops. We chose this over admin-built packs with a signed index: the index would be rewritten in place, so it can't sit under the `ops/` lock, packs would need their own format and checks, and the admin would become a bottleneck that can't re-pack ops kept only as headers. Packs are only containers, so nothing about verification, forks or the checked mark changes. The costs: op bytes are stored about four times (about a cent a month at 300k messages), writers make about 7% more uploads, and removed members' logs stay in small segments, since only an author can pack (#217). Applying, at about 2,550 ops a second, is now the floor for a large catch-up (#216).

## Voice huddles: rules in the core, media through iroh-live (2026-11)
A huddle is a drop-in voice room per channel, as a full mesh over the workspace's own iroh endpoint, so the members-only admission covers it and a removed member is cut off by hanging up. WebRTC is out: WebKitGTK ships without `RTCPeerConnection`, and mobile will be native. The core owns who is in a huddle, from signed, short-lived beacons (gossip for public channels; direct messages to the channel's members for private channels and DMs, so others can't see a private huddle exists), and one hearing rule: you hear exactly the people who can hear you, both being the verified roster that are still members. n0's iroh-live moves the sound (capture, sonora echo cancellation, Opus, jitter, playback) behind one interface of ours (`HuddleMedia`), pinned to a reviewed commit, with our own wire number in beacons so mismatched versions ask to update instead of failing silently. Media paths are random per join, so they name no channel. Nothing is stored: no call log in the bucket or the op log. Mute closes the microphone, so the OS indicator goes dark. With a Bluetooth headset as output, the built-in mic is the default, so the headset stays out of its call mode. On PipeWire the system's default devices are virtual ones that don't say they're Bluetooth, so for now the rule applies when the headset is chosen in the huddle settings. Only iroh-live's node and its audio crate (moq-audio) are built, without its video stack, so no H.264 codec (openh264) is in the app; video and codec licensing get their own decision later (#205). Up to 8 people at first; a forwarding member and SFrame keys from the MLS epoch come later for bigger huddles and video. The rejected options and their reasons are on #15.

## Updates through Tauri's updater, from GitHub releases (2026-11)
Every device should run the same version, so updating has to be easy. Tauri's own updater (one plugin, maintained with Tauri) fetches `latest.json` from the latest published GitHub release and checks each package against a minisign key built into the app; no update server of ours. The whole flow runs in Rust commands, so the page can't install anything itself, a huddle can't be cut off by a restart, and unsent changes are uploaded first. A downloaded update waits in memory until the restart (an AppImage is about 100 MB), rather than installing early: an early `.deb` or `.rpm` install would raise an administrator prompt out of nowhere. Releases are published as normal releases, since GitHub's "latest" skips pre-releases. On Linux the AppImage updates silently; `.deb` and `.rpm` installs update with an administrator prompt.

## New kinds of op keep the op format (2026-11)
An author's ops apply strictly in order, so an op an older app has to wait for holds back everything after it from that author. Signing a new kind in a newer format would make an older app wait at the admin's first workspace icon or look change, holding back the admin's later messages, deletes and new bucket keys until it updates. New kinds (the workspace icon and look) are therefore signed in the same format. An older app skips one as unreadable, keeps it whole and goes on; the new version raises the view rules (`storage::VIEW_RULES`), so an updated app rebuilds its views from the log on opening and applies what it kept. Until then it just doesn't show the icon or look.

## Theme pairs, with the workspace's look as a default (2026-11)
Six named themes, each a light and a dark side, so a workspace can feel like its own place and people with low vision get a Contrast theme. The accent stays a separate choice, so a theme never fixes a colour that could clash. An admin's theme and accent are only a default: someone's own pick always wins on their device. Picking the theme or accent the workspace uses means "follow the workspace", so an admin's later change reaches them; we chose this over a separate "Use the workspace's" option, which would be one more control for the same idea. The core stores the names without knowing them, bounded to short lowercase words, so a new theme needs no core change and an older app shows the default for a name it doesn't know.

## Previews read messages with a markdown parser (2026-11)
One-line previews used regular expressions to name links, and an author could slip a false name past them with spellings markdown allows (`[@Ada](<shy://member/…>)`, brackets inside the label), so a preview read "@Ada" for a mention of someone else (#250, #261). They now parse the message with `mdast-util-from-markdown`, the parser already under react-markdown (a direct dependency on the same version, so nothing new is shipped), and name each link by what it opens. GFM extensions are left out: they never change where a link points, and their one mark a preview would show (`~~`) is dropped as text.

## A patched emoji picker, until upstream has the fix (2026-11)
frimousse reads its store when a part of the picker renders and subscribes only in a later effect, so an update landing in between is lost: on a slow machine a search typed as the picker opened left the full list on screen (#268, upstream liveblocks/frimousse#41). Our code can't close it, because every part of the picker reads that way. So `apps/desktop/patches/frimousse@0.4.0.patch` makes the hook read once more after subscribing, in the ES module build the app loads. pnpm refuses to install if the patch no longer matches the installed version, so an upgrade can't drop it silently. Remove it once a frimousse release has the fix.

## macOS notifications through Apple's notification center (2026-11)
Tauri's notification plugin uses macOS's old notification API and always answers that notifications are allowed, so someone who missed or refused the first prompt got silent alerts and no way to tell. The app calls Apple's `UNUserNotificationCenter` itself through `objc2-user-notifications` (macOS only, already in the dependency tree through Tauri): it reads the real permission, asks once, points to System Settings when refused, and offers Reply and Mark as read. Those calls need `unsafe`, so the desktop crate denies it instead of forbidding it, and only `notify_macos.rs` allows it, each block with its reason. `user-notify` wraps the same API, but is LGPL, brings tokio and more, and panics off the main thread. Linux and Windows keep the plugin; their own notification buttons are #270.
